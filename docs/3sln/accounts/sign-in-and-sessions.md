# Sign-in, passkeys and sessions on 3sln.me

> **Group:** 3sln.me reference service
>
> **Status:** implemented locally (Worker and Node adapters) as 3sln.me account policy; provisional; production release remains disabled and nothing here is production-verified. Hosted email delivery is a configured external service with its own verification.
>
> **Covers:** how 3sln.me signs in its own account holders: passkeys, sign-in emails and their email sign-in links, the hosted recovery-file transaction, browser (owner) sessions and their management, carrying a pending intent or app authorization through sign-in, and the app-session lifetime values 3sln.me chooses within the Bindle ceilings. Passwords were dropped (owner approval 2026-10-28).
>
> **Does not cover:** approving a sign-in from another device. A signed-in browser approving another browser (**session handoff**, which yields an ordinary 3sln.me session) and a CLI or TV app signing in with a code (**app sign-in with a code**) are in [approve a sign-in](approve-a-sign-in.md). App grants and their lifetime ceilings are Bindle rules: [auth](../../spec/auth.md) and the [device authorization](../../spec/extensions/device-authorization.md) extension. Device authorization does not replace or supersede anything here: it issues an app grant, not a provider session.

This document is the 3sln.me reference service's own sign-in policy. It is not part of the Bindle specification; another provider may sign its users in however it chooses. It was formed on 2026-10-27 from the passkey and session parts of the former `device-login.md` and the hosted-account sections of the former auth spec (local clients spike CR-A1). The design behind the 2026-10-28 changes (sign-in emails, dropped passwords, the sign-in continuation) is the [sign-in and intents spike](../../architecture/sign-in-and-intents-spike.md); its owner decisions are listed in its §0, and its email-link protocol (§4), method-removal process (§6.4) and password removal plan (§6.3) remain provisional.

## Sign-in methods

The web sign-in methods are **passkeys** and **sign-in emails**, plus approving a new browser from a signed-in one ([approve a sign-in](approve-a-sign-in.md)). There are no passwords (owner approval 2026-10-28): sign-up, sign-in, step-up, approval, recovery setup and identity-transfer enrollment use a passkey, and `/api/auth/login/password` and `/api/auth/password/pending` answer exactly like any other unknown account route. Authority derived from a password is refused at use time, so this holds on every host before the reset runs (review 2026-10-29 L1): a session a password created or stepped up, any session approved from one, an activation session of a record that still carries password fields (a password sign-up), an approved-but-unconsumed linked request whose approver is such a session, and an app lineage approved before password removal from such a session (or, while the record still carries password fields, one whose approving chain is no longer on the record). The operator boot principal keeps its own password option until the owner answers the spike's open question N5. Records written earlier are cleaned by the bounded reset `passwords-retired-v1` (`packages/identity/password-retirement.mjs`): accounts with a passkey or sign-in email lose their stored password fields and password sessions, and password-only identities and password sign-ups are tombstoned (development data only; there are no users). The reset is revision-checked: a record that changed after it was planned (a recovery started, a passkey added) is planned again rather than deleted (review 2026-10-29 L2). The Node adapter runs it once per data directory at boot; the Worker runs one time-bounded batch per cron trigger and per lifecycle scheduler run or alarm, with its cursor and completion marker in the `LifecycleScheduler` object.

Step-up and recent authentication are passkey only. An account that can sign in only by email may use a fresh email-sign-in session for exactly three things (spike SI-4): adding a passkey, verifying an extra address, and turning sign-in on for another address (within 5 minutes). A passkey added this way records `addedBy: email` with the sign-in email and session that added it, and every channel is notified, so the owner can undo it by RM-3 below (review 2026-10-29 M1; spike Q8). Such a session cannot reissue the recovery file (the account must add a passkey and keep it 7 days), approve another sign-in, remove a method other than by RM-3, choose the notice address, delete a verified address, transfer or delete the identity: SI-4 does not list them, so the owner adds a passkey first. Sessions from the cross-device code path (`email-cross-device`, spike N2, recommendation implemented behind `EMAIL_FLOW_V2`; provisional) may add a passkey and verify an extra address, but cannot turn sign-in on for another address or undo anything by RM-3.

**Provisional passkeys (spike N2, widened by a coordinator decision of 2026-10-29 after the P3 security review H1; provisional, unsigned: Reviewer ___ Date ___ Outcome ___).** A passkey added under email authority is **provisional for 24 hours** (`provisionalUntil`): one added from any email session (`email` or `email-cross-device`), and one registered while setting up an account created from a create-account link. It signs in at once. For those 24 hours it counts for nothing in any authority check: a sign-in with it creates a `passkey-provisional` session, which is not recent authentication (`recent()`), never satisfies LA-7, gives no federation `auth_time` and is no known-device evidence in an identity move; the passkey cannot step up (`passkey_provisional`; the step-up prompt says when it will count), so it never satisfies `privileged()`. It therefore cannot delete the account, export data, remove a method, reissue the recovery file, revoke other sessions, turn sign-in on for another address, rename a passkey or approve another sign-in. Any passkey (provisional included) ends the SI-4 email step-up, so for those 24 hours an email-only account also adds no further passkey and verifies no further address (fail closed: a mailbox holder cannot fill the five passkey slots). Whatever is added traces its provenance in `addedBy` (`email`, `email-cross-device`, or `passkey` only for fresh non-provisional passkey authority), so RM-3 can undo email-added methods. After 24 hours the passkey is an ordinary one (still a recent method under §6.4 until it is 7 days old). This closes the earlier gap where an email session added an ordinary passkey, stepped up with it and then passed `privileged()` (deletion, export).

## Passkeys and browser sessions

An owner can enroll up to five verified passkeys, inspect safe credential metadata, rename labels and remove a credential. Enrollment is a fresh WebAuthn registration ceremony bound to the exact RP/origin, account, expiring challenge and initiating owner session. Enrollment, removal and session revocation require a session authenticated within 15 minutes and exact-origin/session CSRF checks. Removing a passkey is a sign-in method removal (spike §6.4, provisional; review 2026-10-29 M2), with the same tiers as sign-in emails. The floor needs a configured recovery-file hash and another working method: a passkey or a sign-in email (SI-12, `credential_required`); a verified email that is not a sign-in email does not count. A passkey enrolled 7 days or more earlier (or of unknown age) is established: removing it needs Tier B (recovery-file proof and a delay), which is not built, so it is refused with `removal_unavailable`. A passkey under 7 days old is undone at once with a passkey step-up within 5 minutes from an established passkey other than the one removed (Tier A; the console prompts with `step_up_required` when such a passkey exists), or, if an email session added it, from an email session under 10 minutes old on an established sign-in email (RM-3). The proving method always remains, so the remaining method is proven in the same flow. A session holding a freshly added passkey therefore cannot remove the owner's established passkeys. Removing a credential revokes login sessions created using that credential and notifies every channel.

Sessions have opaque management IDs distinct from their authentication tokens. Device lists contain label, creation, last-use and expiry times plus a current-session marker. Session-token hashes and other sessions' CSRF tokens never leave this view. Labels are bounded, untrusted plain text rather than verified hardware descriptions. Existing sessions receive stable derived public IDs without exposing their token hashes. Owners may revoke one selected session, all others or their current session. Last-use persistence is throttled to once per minute; concurrent telemetry conflicts do not fail reads.

## Email addresses and sign-in emails

Implemented locally (owner approval 2026-10-28; field names provisional; `packages/identity/emails.mjs`). Each address on an account is in exactly one state:

| State | Meaning | Receives | Holds the address |
| --- | --- | --- | --- |
| `unverified` | Added by the owner; its session-bound link is outstanding. Expires 24 hours after it was added. | Only its own verification mail. | No: verification fails if another account verified the address first. |
| `verified` | Mailbox control proven. | Security notices; ordinary notices when it is the notice address. | Yes. |
| `sign-in` | A verified address the owner turned on for sign-in links. A full sign-in factor. | Sign-in links, and everything `verified` receives. | Yes. |

- An account holds at most three verified or sign-in addresses and at most one unverified address; a newly added address replaces the unverified one. Exactly one verified or sign-in address is the **notice address** (the first one verified, changeable in Settings with a passkey sign-in or step-up within 15 minutes; a change notifies every address, including the previous and the new one). The notice address receives ordinary notices; every verified and sign-in address receives security notices, including identity-move begin, contest and restart notices (each address with its own dispute token, and each can be named as a disputer), owner-deletion notices and inactivity lifecycle notices (review 2026-10-29 M3). Every verified or sign-in address is indexed for uniqueness in the same repository write; an unverified address never is.
- **Adding** needs recent authentication (a passkey within 15 minutes, or SI-4) and answers the same way whether or not another account holds the address; no mail goes to an address another account verified. The verification mail is sent in the background.
- **Turning sign-in on** is allowed only from `verified` and needs a passkey step-up within 5 minutes (or the SI-4 email step-up on an account without a passkey). A setup code verified during sign-up or recovery setup makes the address `verified`; sign-in is a separate, unchecked choice on the same screen. Every change to sign-in raises the security epoch and notifies every channel.
- **Turning sign-in off or deleting a sign-in email** is a sign-in method removal (spike §6.4, provisional). Implemented: the floor (another passkey or sign-in email must remain, `last_sign_in_method`), Tier A (a sign-in email turned on less than 7 days ago is undone at once with a passkey step-up within 5 minutes from a passkey enrolled 7 days or more earlier) and RM-3 (one turned on from an email session is undone from an email session under 10 minutes old on another established sign-in email). A sign-in email 7 days or older needs Tier B (recovery-file proof and a delay), which waits for the recovery spike's proof-only file presentation, so it is refused with `removal_unavailable`. The removal ends that address's sign-in links and the sessions it signed in. A sign-in email from a record written before this model (`emailLoginEnabled`) counts as established from its verification time, or from time 0 when none was recorded, so it is Tier B at once; this fails closed (it cannot be turned off until Tier B exists), and data resets are acceptable (review 2026-10-29 L4).
- **Deleting a verified address** keeps the DX-6 rules (`EMAIL_REMOVAL_ENABLED`, step-up within 5 minutes, the notice waiver when no other channel exists; other verified addresses count as channels). Removed addresses stay notice channels for 30 days (`previousEmails`). An unverified address can be dropped at any time.
- **Recovery** turns every sign-in email into a verified address and drops an unverified one; recovery setup can turn sign-in back on with a fresh setup code.
- Records written before this model carry `verifiedEmail`, `emailVerifiedAt` and `emailLoginEnabled`; they are read as one entry (a sign-in email when `emailLoginEnabled`) and rewritten on the next identity write.

## 3sln.me email sign-in

Two implementations exist; a deployment uses exactly one:

- **`EMAIL_FLOW_V2` off (the default):** the earlier same-tab link (`emailLoginStart` / `emailLoginConfirm`) for sign-in emails of active accounts. The link binds the address and the moment sign-in was last turned on, so turning sign-in off and on again, or removing the address, invalidates outstanding links; the session records the address it proved. It is a bearer link: it signs in in whichever browser confirms it.
- **`EMAIL_FLOW_V2` on (implemented locally 2026-10-29, phase P3; provisional, unsigned protocol; direction owner-approved 2026-10-28):** the cross-device flow of the [sign-in and intents spike](../../architecture/sign-in-and-intents-spike.md) §4, and the older link routes are refused. The engine is `packages/identity/email-flow.mjs`; the routes (`packages/runtime/routes/email-flow.mjs`) and pages are thin.
  - **One entry point, "Continue with email"** (SI-5). After Turnstile and the mailbox, region and global windows, every start creates a flow record (also on the branches that mail nothing), does the same hashing and writes, and answers `{flowId, expiresIn: 900, interval: 3}`; mail is sent in the background. A sign-in email of an active account gets a sign-in link; an address with no account gets a create-account link while `EMAIL_SIGNUP_ENABLED` and sign-up are open, otherwise a notice pointing at the waitlist; a verified address that is not a sign-in email gets a link-free notice (at most one per 24 hours); anything else gets nothing. A non-completing flow polls `pending` until it expires. At most 3 live flows per address and per browser.
  - **The original tab keeps the flow.** It generates a 256-bit secret `S` and sends only `SHA-256(S)` and a channel tag `T = HMAC(S, "bindle-email-flow-bc")` at start; it keeps `S` in memory and its own `sessionStorage` (a reload resumes). The response sets the browser marker `__Host-bindle_email_flow` (256 random bits, HttpOnly, `SameSite=Strict`, 20 minutes); the record keeps only keyed hashes of the marker and the link token.
  - **The mail** holds `https://3sln.me/email/link#t=<L>`: a 256-bit, single-use token in the fragment only, with no account id, flow id or address; 10 minutes. It names no requesting device and says nobody will ever ask for a code from it.
  - **The helper page** (`/email/link`, its own strict-CSP document with no third-party assets, `no-store`, `frame-ancestors 'none'`, COOP `same-origin`) removes the token from the address bar; GET does nothing. Its first request (`inspect`) is read-only and shows the request from server-captured context: the account handle (or the masked address for a sign-up), the browser family and system, the edge's approximate location (city, region or country; never an IP; labelled approximate) and the time, and whether this browser asked for the link or "Another device asked for this link" with the phishing warning. Its controls are inert until the page has been visible and focused for 600 ms, none takes default focus, and "No" asks again before cancelling. Nothing on this page creates a session by itself.
  - **Same browser:** "Yes" approves (the marker must match again; the link is used up) and posts a BroadcastChannel wake-up tagged with `T`. The original tab accepts only its own flow id and tag (constant time), acknowledges, and polls at once; the wake-up carries no authority. Otherwise the original tab polls every 3 seconds (`slow_down` when faster).
  - **Another device:** "Yes" reveals a 6-digit code (5 minutes, capped at the flow's expiry; at most 3 reveals of the same link show the same code, which the server re-derives and never stores). The person types it into the original tab, which redeems with `S` and the code. Five wrong codes lock the flow; code attempts are also charged per network prefix (20 per hour) and against a global budget scaled to live codes, after which a code redemption needs a fresh Turnstile proof. Every attempt is reserved before the code is compared (the flow's attempt by compare-and-swap, the prefix and global budgets by charging first; a correct code spends one budget unit), so parallel guesses cannot exceed any of these limits (P3 security review L2).
  - **Redemption** needs `S` (and the code on that path), consumes the flow by compare-and-swap, re-checks that the account is active, the address is still a sign-in email with the same `signInSince` and the security epoch has not risen since start, then mints a fresh session (`email`, or `email-cross-device` on the code path) and notifies every channel (`email-sign-in`, naming the requesting browser, system and approximate place from the fixed vocabulary). The 5-account browser cap is checked before anything is consumed: a refused redemption leaves the flow redeemable and sends no notice (P3 security review L4; residual: a concurrent sign-in in the same browser can still be refused at installation after the notice). The original tab then resumes its own continuation (an intent or app authorization entry).
  - **Closed original tab:** when the original tab does not acknowledge within 2 seconds and has not redeemed, the helper (same browser, marker required, approved flow) offers "sign in in this tab instead" as a separate explicit act; any continuation is dropped.
  - **Cancel and resend:** the helper's "No" ends the flow (a security notice for a sign-in flow); the original tab cancels on Cancel or when it signs in another way; "Send a new link" re-mails a new token for the same flow (older links die; at most 3 per flow). A resend counts as a send: it charges the same mailbox windows as start (5 per 15 minutes, 12 per 6 hours, keyed by the flow's mailbox pseudonym on every branch), so starts and resends together mail one address at most 12 times in 6 hours and a resend needs no Turnstile of its own (P3 security review L1). The helper document is served only at `/email/link`; its static path `/email-link.html` answers like an unknown page (I1). The original tab's BroadcastChannel acknowledgement carries `T` too (I3). Start reads the same storage for a known and an unknown address (the repositories read a random account key on a miss; L3); CPU and storage latency still differ slightly, so deployed timing parity remains a release gate. Flows expire after 15 minutes; terminal records are purged 24 hours after expiry.
  - **Not implemented:** cancelling on `pagehide` (it would end the flow on a reload, which must resume); the one-click "This wasn't me" lockdown in the sign-in notice (the notice says how to secure the account; a release gate); a "Continue as `<handle>`" step on the original tab (SI-11 places it after redemption; the tab shows "Signed in as `<handle>`", or the intent page's explicit account choice, after redeeming; I2); detecting an unverified entry elsewhere (unverified entries are not indexed, so such an address is treated as having no account). Delivery and the edge geo source are external; local tests prove the protocol, not delivery.

The table below is the general email-flow outcome policy; with `EMAIL_FLOW_V2` on, the cross-device rows are answered by the protocol above (a link opened elsewhere never signs in by itself).

Sending email never creates an account. A request creates an expiring verification challenge, with purpose `login` or `link`, a hash of a random secret (at least 256 bits), intended email, initiating account for linking, initiating browser transaction, and allowed return target. Replies are generic regardless of account existence. Apply mailbox/IP/device/global rate limits without permanently locking a mailbox due to an attacker's requests. Reference host (wargame 2026-10-23, provisional): after the Turnstile check, a pseudonymized mailbox window (5 per 15 minutes and 12 per 6 hours), a regional window (5,000 per hour) and a global ceiling are charged whether or not the address has an account; both branches do the same token work, and the challenge write and the provider call run in the background on a hit (the platform's `waitUntil`), so neither latency nor provider errors reveal whether an address can sign in. Only registered redirect targets are accepted; links cannot carry arbitrary return URLs.

Magic links are valid for ten minutes and single-use. GET renders a confirmation page and MUST NOT consume the token, create an account, associate an email, or authenticate: mail scanners prefetch links. Redemption is an explicit CSRF-protected POST. Token material must be removed from the address bar after delivery into a temporary server-bound interaction; use `Referrer-Policy: no-referrer`, no analytics or third-party assets, and scrub query strings from logs. Cross-device links can complete mailbox verification, but cannot approve the initiating app's authorization transaction without a fresh flow on the consuming browser. Show the app/provider context; prevent login CSRF by requiring explicit acceptance before replacing an existing session.

Account and email changes run in one database transaction with a unique canonical email ownership constraint and consumed-token compare-and-swap. Domain normalization alone defines canonical comparison; local-part semantics cannot safely be guessed. Repeated redemption returns an expired/used result; it cannot replay success or expose the account.

| Verified challenge and current browser state | Required outcome |
| --- | --- |
| Unclaimed email; no session | Explain new account, obtain explicit account creation confirmation, then create subject and associate email atomically. |
| Email belongs to A; no session | Explicit login confirmation authenticates A. No account creation. |
| Unclaimed email; already signed into A; login-purpose link | Offer attach to A or create a separate account. Neither happens automatically. Attaching requires recent A authentication and explicit confirmation; separate account switches session only after confirmation. |
| Email belongs to A; signed into A | Confirm same account; complete eligible login transaction. |
| Email belongs to B; signed into A | Explain different account; offer cancel or explicit switch to B. Never attach B's email to A, transfer it, or merge accounts. |
| Link-purpose challenge initiated by A; signed into A | Require recent authentication and explicit attach; atomically claim only if unclaimed or already A. |
| Link-purpose challenge initiated by A; no session | Require login to A before continuing; mailbox proof alone cannot authorize modification of A. |
| Link-purpose challenge initiated by A; signed into B | Require switching/authenticating A; do not rebind the challenge to B. |
| Email claimed by another account after link sent | Reject attachment, preserve ownership; offer separate login flow. |
| Expired, used, malformed or wrong-purpose token | Generic invalid-link screen and explicit resend; no mutation. |
| Token forwarded or opened on another device | Mailbox token is transferable proof; present full context, require explicit acceptance, and begin a fresh app authorization transaction on that device. |
| Email removed after challenge issued | Account/email revision check invalidates outstanding login challenges; fresh flow reflects current ownership. |
| Account deleted/suspended after challenge issued | Reject; do not resurrect or silently rematerialize the account. |
| Concurrent redemption/create/link | Exactly one atomic transition succeeds; uniqueness prevents duplicate ownership. |
| User changes mailbox input during flow | Issue a new challenge; never retarget an existing token. |

Account settings list verified emails, verification dates, primary contact, passkeys, sessions, and grants. Adding/removing emails requires recent authentication; new addresses must be verified. Notify existing contact channels of sensitive changes without leaking secrets. Removing an email invalidates its outstanding challenges. Never permit removal of the last usable recovery/login method without enrolling another. Mailbox proof is a recovery factor; administrators must not invent bypass merges. Account merge and identity migration are explicitly outside v0.

Email authentication proves current mailbox control, not legal identity or durable ownership. Recycled mailboxes can recover accounts still linked to them. Explain this when enabling email recovery; users may opt out of email recovery after enrolling sufficient alternative credentials. A passkey-protected account configured without email recovery MUST NOT be recovered through an email login link. A verified email may remain a contact address without being an authentication method: hosted account records keep each address `verified` until the owner turns it into a sign-in email (see "Email addresses and sign-in emails" above); verifying alone grants no sign-in authority. Both link issuance and redemption check the current state, and removing sign-in removes outstanding login challenges so turning it on again cannot revive an old link.

## Hosted recovery-file transaction

The original recovery file starts one pending recovery transaction and revokes old sessions and authenticators. Its hashed resume authority remains only while that account is recovering, so lost HTTP responses or an expired 30-minute setup token do not strand an account with no other recovery channel. A CAPTCHA/rate-limit guarded resume rotates the limited setup token without clearing completed replacement credentials. The user must still prove possession of a newly downloaded replacement file and confirm saving it before activation. An active owner can replace the file (the active-account reissue); a reissued file cannot start a recovery for 7 days and the previous file can only cancel the reissue during that window ([recovery identity](recovery-identity.md#active-account-reissue-provisional)). Activation atomically removes the original file’s resume authority; it cannot replay completed recovery or issue a full session on its own. Setup and resume secrets never enter audit events or logs.

## Passkey verification

Use maintained server-side WebAuthn verification, not handwritten cryptography. 3sln fixes its RP ID and permitted HTTPS origin list in deployment configuration; never derive them from request headers. Challenges are random, single-use, short-lived, and bound to purpose and session. Validate challenge, origin, RP ID hash, type, signature, user presence and required user verification. User handles are stable opaque bytes unrelated to email. Registration requires an authenticated recent session; login uses discoverable credentials or an explicit handle, with enumeration-safe errors. Reference host (wargame 2026-10-23, provisional): the handle-login challenge is not stored; the begin token is `pl1.<payload>.<mac>`, a keyed MAC over {handle, challenge, nonce, expiry}, so begin reads no account, writes nothing, reveals neither an account id nor whether or in what state a handle exists, and cannot evict another caller's challenge. Finish verifies the MAC and the assertion, then records the nonce as used in the session's own write (single use). Sign-in abuse windows: only per-network windows run before Turnstile; passkey begin and finish never touch a per-handle window, so nobody can lock a handle out. Store credential public keys, IDs, transports, backup flags, counters and a user-chosen label. Synced passkey counters can be nonmonotonic; evaluate anomalies without assuming every zero/nonincrease is a cloned authenticator.

Require user verification for account management and passkey login. Do not require attestation for ordinary individual users. Offer enrollment after materialization, additional passkeys, last-used metadata, and removal with recent authentication and recovery-method checks. Passkeys remain provider-scoped: a self-hosted provider uses its own RP ID. Lost-device recovery follows the user's configured factors; no automatic downgrade to email when disabled.

## Carrying an intent or app authorization through sign-in

Implemented locally (spike SI-8, owner-approved 2026-10-28; phase P1; `apps/web/src/shared/continuation.mjs`). When someone opens an intent link or an app authorization page while signed out, the original tab keeps what they were doing in one `sessionStorage` record (`3sln-continuation`): the intent value and placement, or the authorization return target. It is never in a URL, an email, a cookie or a server record. It expires at most one hour after capture and is never extended (for an intent, at the intent's own expiry). Return targets are a closed set (`/i`, `/oauth/authorize?request_id=…`). Every in-browser sign-in path (passkey, approving this browser from another device, sign-up activation, an email link opened in the same tab) ends in one step that resumes it; completing a recovery, signing out, signing out the tab's account and switching accounts discard it (review 2026-10-29 L3). With an intent pending the tab returns to `/i`, which takes the value once and asks for an explicit account choice when several accounts are signed in. This replaces the two earlier stores, whose 10-minute console entry dropped an intent that took longer to sign in for. Email links opened on another device will join this flow with the email-link protocol (P3).

## App session lifetimes on 3sln.me

These are 3sln.me's values within the ceilings of [auth §"Token lifetime and client sessions"](../../spec/auth.md#token-lifetime-and-client-sessions) and [device authorization §7](../../spec/extensions/device-authorization.md#7-credential-lifetime) (user decision 2026-10-20, provisional):

- Access tokens: at most 15 minutes (Bearer) or 60 minutes (DPoP-bound), configurable shorter with `APP_ACCESS_TOKEN_MINUTES` and `APP_DPOP_ACCESS_TOKEN_MINUTES`. 3sln.me issues Bearer access tokens alongside a DPoP-bound refresh token (proposed).
- Client sessions have no absolute lifetime. The idle limit is 180 days since the last refresh (`APP_REFRESH_IDLE_DAYS`, 1–365), for every app grant, authorization code and device grant alike.
- A replayed authorization code revokes the client session from its first redemption; 3sln.me keeps a 10-minute redeemed-code marker for this (provisional, 2026-10-23).
- Durations offered when approving an app with a code are in [approve a sign-in §7](approve-a-sign-in.md#7-lifetimes).
