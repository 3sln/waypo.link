## Identity and artifacts

The identity is an immutable, canonical lowercase UUIDv4. A free or paid name routes to that UUID and may be certified separately. Recovery must not depend on the current spelling, preferred alias or availability of a name. The identity signing key belongs to the UUID and stays in provider custody (sealed under `KEY_ENCRYPTION_KEY`); it rotates with continuity statements under its own rules and is never exported to the user. The separate identity encryption key was removed (no consumer; owner approval 2026-10-28).

| Artifact | Contents and handling |
| --- | --- |
| Encrypted recovery file | Opaque payload v3 `{version:3, issuer, entity, recoveryToken, fileId, issuedAt}` inside answer-derived authenticated encryption ([recovery file](recovery-file.md)). No handle, alias, assignment identifier, name certificate, private key or provider signature. `fileId` is also in the public header. |
| Public name certificate | Provider-signed issuer, UUID, exact canonical handle, assignment identifier and issuance time. No private keys, reset credentials or private recovery proof. Download separately; it can be shared as evidence of historical assignment. |

Changing or adding a name does not require a new recovery file. A name certificate is historical issuance evidence, not a current login credential or a permission grant. A certificate supplied with its own untrusted verification key does not establish provider authority.

The recovery file restores access to the same UUID at the live provider; it cannot be used anywhere else, and it cannot reconstruct deleted grants, revive revoked permissions or recover missing messages/files. Contact links were removed from the core in contacts phase 4 (2026-10-28); people reach an account through its messaging app's invitations, which recovery does not restore. Existing provider OAuth credentials, application consents and passkey private keys are outside the recovery file.

## Recovery wire schema and API

The outer `3sln-recovery` envelope is version 2 (version 1 plus the public `fileId` header member), with the unchanged Argon2id, normalization, AES-GCM, bounds and every-answer requirements. The payload is versioned independently as version 3. The parser and cryptography are `packages/recovery/index.mjs` (`createRecoveryPayload`, `validateRecoveryPayload`, `encryptRecoveryFile`, `decryptRecoveryFile`, `inspectRecoveryFile`, `recoveryFileDigest`).

The provider issues the payload: a random 256-bit reset credential `<entity>.<base64url>`, whose domain-separated hash it stores, and a random 128-bit `fileId`, which it stores in clear beside the hash with the issue time. Recovery and the previous file's cancel present only the decrypted credential; the provider checks its hash. The browser checks the payload schema and that `issuer` is the selected provider; there is nothing else to verify. Envelope version 1 files (payload v1 with a handle, signed payload v2 with a keychain and provider proof) are not recognised any more (owner approval 2026-10-28): the browser refuses them before key derivation, and a stored credential of that format starts no recovery; the console asks for a new file (`reissueRequired: 'legacy-format'`).

Withdrawn with v3 (kept here for the record): the provider-signed v2 identity backup (`createIdentityBackup`, `verifyIdentityBackup`, `3sln-identity-backup-v2` proofs), the keychain in the file, the server's key-equality check at recovery, the rotation of the signing key at every file issuance (P15) and the recovery kid binding in `keys.mjs`. The portable identity package and transfer-in from files are dormant: transfer-out refuses with `recovery_invalid` (no file proves key possession), and the browser's package builder refuses v3 payloads. Their removal and the portability spec revision are phase 2 of the spike.

## Separate name certificate API

```js
createNameAssignment({issuer, entity, handle, assignmentId, issuedAt}, authority)
verifyNameAssignment(certificate, authority, {issuer, entity, handle, assignmentId})
```

The result is `{version:1,type:'3sln-name-assignment',issuer,entity,handle,assignmentId,issuedAt,proof}`. Its proof signs UTF-8 `3sln-name-assignment-v1.ES256.<provider-kid>.<payload>`, where payload contains the canonical public fields only. Signing and verification use a distinct purpose from recovery. Copying a recovery proof into a name certificate fails verification. The creator accepts only the exact public inputs; passing a keychain or reset credential fails rather than silently serializing it.

Certificate handles must already be in the canonical form returned by the shared namespace parser. Lookup accepts supported case/Crockford spelling variants, but certificates retain the exact signed canonical spelling. The assignment identifier binds the retained identity assignment lineage; several name claims for the same UUID may share it. Exact issuer, UUID and handle disambiguate each signed name. A new paid alias receives a separate name certificate and does not modify the recovery payload or the canonical free name. The name certificate does not promise data retention or authorize restoration of a deleted account.

## Provider trust and custody

The provider name-certificate signing private key (`RECOVERY_SIGNING_KEY`) is independent of user keys and `KEY_ENCRYPTION_KEY` and never enters an artifact; it signs name certificates only (recovery files are no longer signed). Node development adapters persist it with private filesystem permissions across restarts; deployed adapters require explicitly configured stable authority. `GET /api/recovery/authority` serves its public key for name-certificate verification. Verify certificates against the independently selected provider's trusted key, never an issuer URL, key URL or bundled authority chosen by the file. Provider rotation requires retained trusted verification history and an explicit compromise policy; configured credentials and local signatures are not evidence of production custody or external conformance.

## Retained-account recovery

1. Require the existing limited setup authority, or an owner session under the rules of [active-account reissue](#active-account-reissue-provisional). Issue a v3 payload and commit its credential hash, file id and issue time under identity revision/CAS checks. Do not return a usable payload after a failed commit. No key is created, rotated or exported.
2. Encrypt the payload in the isolated first-party recovery document. Setup retains every-answer local decrypt verification and explicit save acknowledgement before activation; reissue additionally requires the re-upload acknowledgement ([recovery file](recovery-file.md)). Neither proves a copy exists off this device.
3. On restore, decrypt locally, check the exact schema and the issuer, and send only the credential with the abuse proof. The server checks it against the current v3 credential or its active transaction resume credential. Name state is not an input to recovery.
4. On first recovery revoke old passkeys and sessions, turn every sign-in email into a verified address, preserve a transaction-scoped resume hash, and enter recovering. Resumption preserves newly completed setup. Replacement-file confirmation atomically reactivates the same UUID and removes old resume authority. A consumed token alone cannot start another recovery.

Keep answers, tokens and decoded recovery payloads out of logs, public UI state, telemetry, URLs and browser persistence. A public handle may be returned beside the recovery content for setup display; it is not part of the downloaded encrypted recovery payload.

**Cooling-off window (user decision 2026-10-23 after the identity wargame, provisional; Reviewer ___ / Date ___ / Outcome ___).** The red-team review showed that a stolen password alone became a permanent takeover: step up with the (aged) password, reissue, then immediately `recover()` with the new file, which wiped the owner's passkeys and sessions. The rules (a)–(d) below replace "the previous file stops working at confirmation".

- **(a) Passkey only.** The reissue step-up must be a passkey step-up. Restated without passwords (owner approval 2026-10-28, "drop passwords"; [sign-in and intents spike](../../architecture/sign-in-and-intents-spike.md) §6.3 and §9.3(b), provisional): an account with no passkey (one that signs in only by email) cannot reissue; it must add a passkey and keep it 7 days (`passkey_required`). An email-sign-in session never reissues.
- **(b) The new file waits.** A reissued file cannot start `recover()` until it is 7 days old (`recovery_not_ready`). This mirrors P14, which already kept it from authorizing a move for 7 days.
- **(c) Cancellable for 7 days.** During the window the reissue can be cancelled from: any session created before the reissue **began** (the owner's earlier devices, including the requesting session itself); the link in the confirmation notice, sent only to an email verified before the reissue began; or the previous file (below). Notices go to every channel (email and push) at begin, at confirm and at cancel. Cancelling restores the previous credential, file id and version (and any forced-reissue marker the reissue consumed), voids the new file and bumps `security`.
  - A cancellation also ends every session created at or after the reissue began, plus the session that staged it and the one that confirmed it (`recoveryPrevious.stagedSessionId`, `confirmedSessionId`), and severs app connections (reason `recovery`): the cancel CAS (like a recovery start) writes a durable `pendingSever` row that is retried at recovery activation, at the next owner view and by a later cancel until the port succeeds; a run clears only the row it ran (matched on `at`), so a newer row waits for its own run. The account side severs connections first, then revokes every remaining key delegation.
- **(d) The previous file is cancel-only, and only after a reissue that is not file-proof.** It may be the stolen one, so during the window it never starts a recovery. After a reissue confirmed with a passkey that is **not file-proof** (see below; formerly also any password-authorized reissue) it can cancel the pending reissue (`recovery_reissue_pending`; `/cancel-file`, with the previous v3 file's credential; a legacy previous credential cannot cancel) and gets its full authority back only through that cancellation; otherwise a password thief could lock a password-only owner out. After a **file-proof** reissue it can neither recover nor cancel (`recovery_reissue_locked`, `reissue_cancel_not_allowed`): that reissue may be retiring a leaked file, so only earlier sessions and devices and the current pre-reissue email can cancel it. Coordinator decision 2026-10-23, provisional; Reviewer ___ / Date ___ / Outcome ___. Passwords are to be dropped (owner approval 2026-10-28, a later change); the password branch lives only in `IdentityService#fileProofReissue` (the `fileLocked` flag) so it can then be removed in one place.
  - **File-proof** (independent review 2026-10-23, R1(i), provisional; Reviewer ___ / Date ___ / Outcome ___): the step-up was a passkey **enrolled before the previous file was issued**, and **no channel-removing event happened at all in the 30 days before the begin**, whatever its order relative to the passkey (re-verification 2026-10-23, V1; the first version only counted events after the passkey's enrolment). Channel-removing events are recorded in an uncapped monotonic `account.lastChannelRemovalAt`, which the check reads (final check 2026-10-23, V2: a capped list that kept its earliest entries let filler events push a later removal out); `account.authorityEvents` keeps only the newest 16 for display. They are: an email change or removal, revoking other sessions, a session-cap eviction (signing in an 11th session evicts a live one) and a passkey removal. The check is evaluated at the begin and again at confirmation, both anchored at the begin time, so an event inside the lookback at the begin still counts if it ages out before confirmation. Anything else is not file-proof (the former "password branch"). This closes the review's takeover: a password thief who enrols their own passkey, swaps the email, waits and revokes the owner's sessions makes a reissue the owner's file can still cancel. `recoveryPrevious.fileLocked` records the outcome at confirmation.

Representation: confirmation keeps `account.recoveryPrevious` = {hash, issuedAt, fileId, version, marker, reminder, reissuedAt, preparedAt, until, newFileId, cancelHash, credential, fileLocked} beside the new current credential. `pendingReissue(account, now)` is the live window. The window ends by time (the record is ignored, then dropped by the next recovery or reissue), or by cancellation. A recovery started after the window (with the new file) drops it.

**Edge cases.**

- **No passkey.** The account cannot reissue until it has had a passkey for 7 days (passwords were dropped). Formerly: the reissue needed an aged password. Cancel channels are the sessions that predate it and the previous file. The owner who still has the file is protected; one who has lost both the file and every earlier session cannot cancel, which is the same position as an owner without a file today.
- **Email changed before the reissue.** A verified email that is replaced or removed is kept for 30 days (review R1(iii); 7 days in the first version; stored one hour longer so a confirmation up to 30 minutes after a begin still finds it) in `account.previousEmails` (up to 8 within retention; a further change is refused with `email_change_limited` rather than dropping one, so no swap sequence can push the owner's address out). Reissue notices at begin, confirm and cancel go to the current email and to every email replaced in the 30 days before the begin (confirmation notices are anchored at the begin). Because a replacement is itself a channel-removing event in the same 30-day lookback, a reissue that sees a replaced address is never file-proof, and one begun after the lookback finds neither. After a reissue that is not file-proof the cancel link goes to each of them that was verified before the reissue began; after a file-proof reissue it goes only to the current pre-reissue email, and replaced addresses get the notice only (review R2: a replaced address may be the compromised one the owner retired). So an attacker who swaps the email (which needs only a recent sign-in) and then reissues does not silence the owner's address. An email verified after the reissue began gets the notice but no cancel link; one replaced more than 30 days earlier gets nothing.
- **Security notices** (review R1(ii), V1). Adding or removing a passkey, changing or removing the email, signing out other devices, a session-cap eviction, turning a sign-in email on or off and registering the replacement passkey during a recovery notify the current email, every email replaced in the last 30 days and push, each saying how to respond (`IdentityService#queueNotice`, sent after the record's commit through the existing security-alert templates and push security-notice events). Notices are coalesced per account and type, and only for repeats by the **same** acting session or credential within 10 minutes; a different actor is always notified at once (final check N1). A coalesced count is sent as a trailing notice at the account's next write or owner view after the window (`account.noticeLog`). Known limit: there is no identity-side alarm, so if nothing touches the account after the window the trailing count waits; the first event of every actor is never delayed. Passkey enrolment begin is rate limited per account and network. Coordinator decision 2026-10-23, provisional; Reviewer ___ / Date ___ / Outcome ___.
- **Reissue during an active recovery.** Impossible: a recovering account has no owner sessions, and a staged reissue is discarded when a recovery starts. A recovery cannot start during a window with either file, so a window and a recovery never overlap; a recovery started after the window drops `recoveryPrevious`.
- **One window at a time.** A new begin is refused (`recovery_reissue_pending`) while a window is open. Otherwise a second reissue would push the trusted previous file out of the window. The owner who wants a different file cancels first.
- **Authority epoch (`aep`).** A reissue and its cancellation do not raise `aep`; no one inherits the identity at that moment. The recovery that eventually uses a file raises it at activation, as before. Organization governance holds therefore start only when a file is actually used.
- **No key changes (v3).** Neither begin, confirm nor cancel touches a key: files hold none. A voided file discloses only its own credential, which never becomes current.
- **OAuth grants.** `federationEpoch` hashes the current recovery credential, so a confirmation revokes every grant. Cancellation restores the old hash, which would revive grants from before the reissue; it therefore also raises `account.federationGeneration`, a monotonic component of the epoch. No grant from before or during the window survives a cancellation.
- **Transfer-out.** Confirmation still cancels a pending or held move. During the window the current credential is younger than 7 days, so P14 refuses any new move. A cancellation bumps `security`, so the 7-day look-back refuses a move for another 7 days even though the restored file is old.
- **Forced paths.** An elevated-abort or transfer-in reissue has no previous credential: the window still applies to the new file; cancellation leaves no current file and re-arms the forced marker. (a) applies to forced reissues too.
- **P17.** The contest check compares the credential that confirmed the step-up (a passkey id), not the one the session signed in with (wargame 2026-10-23).
- **Deletion and custody.** Begin and confirm keep their refusals. Cancellation is allowed during a scheduled deletion (it only restores a credential) and refused once the account is purging or deleted.

**Trade-off of V1 (recorded):** an owner who changes the email (or signs out other devices, removes a passkey, or is evicted at the session cap) and then reissues with an old passkey within 30 days gets a reissue that is not file-proof, so the previous file and the replaced address can cancel. If those are the compromised ones (review R2's scenario), an attacker can cancel the reissue and recover with the leaked file. V1 accepts this to keep the owner's channels alive against a thief who removes them; an owner retiring a leaked file should wait out the lookback after changing the email, or rely on support. Reviewer ___ / Date ___ / Outcome ___.

**Safer variants considered.** As first implemented, (d) let the holder of a leaked file cancel the owner's reissue and recover at once. Two alternatives were weighed: (1) on a passkey-authorized reissue, deny the previous file the cancel right (sessions, devices and email only); (2) send a file cancellation of a passkey-authorized reissue to support (a P17-style contest). **Variant (1) was chosen** (coordinator decision 2026-10-23, provisional; Reviewer ___ / Date ___ / Outcome ___), and a reissue that is not file-proof keeps the file's cancel right. Its cost: an owner whose passkey device was taken and who has neither an earlier session nor a pre-reissue email cannot cancel a reissue made with that device. Variant (2) was not adopted because it adds a support dependency to every leaked-file case.

**Who may reissue.**

- A signed-in owner of an active account, with a passkey step-up in the last 5 minutes made with a passkey enrolled at least 7 days earlier (P18, P19, rule (a)). The step-up records which passkey confirmed it. An account with no passkey cannot reissue (`passkey_required`).
- A forced path, armed on the identity record, waives the credential age, but only for a credential enrolled no later than the moment it was armed. A credential added afterwards still waits 7 days. A fresh step-up is still required. The forced paths are:
  - after an elevated-proof abort, which invalidates the current file and arms the reissue in the same action;
  - at PORT-4 activation, where the destination's recovery port arms it. The file is encrypted in the owner's browser, so activation keeps reporting `recoveryRequired` until the owner downloads.
- Within 30 days after an elevated-proof abort, a reissue by any credential other than the one that aborted is contested and refused (P17). Support then decides.

**What it does.** It runs in two phases, so an interrupted reissue never leaves the owner without a working file.

1. **Begin.** The account single writer applies the refusals below. The new v3 file is **staged** (`recoveryStaged` = {hash, fileId, …}): bound to the requesting session for 30 minutes, not yet current. The current file keeps full authority. A new begin replaces an earlier staged file, which never becomes current. Every channel is notified.
2. **Confirm.** This runs only after the browser has encrypted and downloaded the file, the owner has re-entered the answers, and the owner has selected the saved file again and its SHA-256 matched the downloaded bytes (the acknowledgement; [recovery file](recovery-file.md)). The request carries the staged credential and `fileId`. The account gate runs again and a pending or held transfer-out is cancelled (below). Then one identity CAS makes the staged credential current and opens the window: `recoveryIssuedAt = now` (so P14's 7 days and the annual reminder start again), `recoveryFileId` is the new id, the previous credential moves to `recoveryPrevious`, any forced marker is cleared and `security` is bumped. An abandoned or expired staging leaves the old file current.
3. After the commit, notices go to the verified email (with the cancel link when that email predates the reissue) and to every push subscription. Acceptance is not delivery. The audit entry is visible on every signed-in session, and the console shows the window with a cancel button on earlier devices.
4. **Cancel** (any time in the window, by the channels in (c)): one identity CAS restores the previous credential, raises `federationGeneration`, bumps `security` and notifies every channel.

**Where it cannot run.**

- **Deletion.** It is refused while a deletion is scheduled or executing, after the purge has started, and after the tombstone. A deletion requested after a reissue's gate is ordered after that reissue.
- **A pending transfer-out is cancelled, not refused.** The move was authorized by the file the reissue replaces. The new file is under 7 days old (P14). A move begun in the window between the gate and the identity commit is still cancelled by the transfer-out engine's own check: the epoch and the credential reference changed (`cancelReason`). A new move then also hits the 7-day security look-back at request time. So a reissue can never be used to start or speed up a move, and P14 cannot be dodged. Cancelling is the safe direction. It is consistent with the spec §6.1 rule that recovery and credential changes cancel a move. Refusing would instead stop an owner from retiring a file that someone else is using to move the identity.
- **A contested transfer or the support lock: refused.** Support's "allow" needs the requester to still hold the current file, so a reissue here would be the second self-resolution that P17 forbids.
- **Moved or arriving identities: refused** by the custody fence.
- **An open window: refused** (above).

**Concurrency.** Begin and confirm are linearized in the account single writer against transfer-out steps and commits and deletion. The identity CAS trails them.

- An identity CAS that loses returns no file and changes nothing else.
- There is one staged slot per account and at most one window.
- A recovery started with the current file before a confirmation discards the staged file and any forced marker. Its sessions end, so no confirmation follows.
- A cancellation whose identity CAS loses retries against the same window (`reissuedAt`).

**Known residuals (unsigned).**

- After a reissue that is not file-proof a holder of a leaked previous file can still cancel it and recover; after a passkey-authorized one, an owner who lost the passkey device and has no earlier session or pre-reissue email cannot cancel (see "Safer variants considered").
- Replaced emails are retained for 30 days for this purpose (`previousEmails`), which the privacy notes must mention.
- An owner who enrolled their only passkey after the current file was issued gets a reissue that is not file-proof: the previous file can cancel it.
- A transfer cancelled by a confirmation whose identity CAS then lost stays cancelled. That is the safe direction.
- The owner's "reissue" choice after a dispute (spec §6.2) invalidates the file without arming the forced path. An owner without an aged credential therefore has no current file until one ages.
- Notices reach emails replaced or removed in the last 30 days (`previousEmails`), not older ones.
- The re-upload acknowledgement is a browser-side check; a modified client can skip it. It protects the owner from a failed or misplaced save, not from a malicious client.
- The annual reminder's email/push delivery has no scheduler yet; the console banner works on the next visit.

## Return, compromise and missing state

For retained accounts, returning restores access to the same UUID (its keys never left the provider); expired, revoked or absent grants remain denied. Recovery is not full compromise remediation: it preserves identity keys, email-login settings and resource permissions. It does **not** preserve OAuth app authorizations: the grant epoch (`federationEpoch`, `packages/runtime/federation.mjs`) hashes the current recovery credential, so starting a recovery, confirming a reissue or cancelling one revokes every app family, code and token, and apps must be authorized again (the safe direction; reconciled with the code 2026-10-23). A monotonic `federationGeneration` on the identity record also feeds the epoch; it rises when grants must end without a credential change (reissue cancellation, suspension), so a restored credential or a reopened account never revives an older grant. MCP grants record the same app-grant epoch at approval and are refused on verify, execute, exchange and refresh once it changes (`packages/runtime/grant-epoch.mjs`; legacy grants fail closed). Recovery start and reissue cancellation also sever every app connection (integrations §7) and revoke every key delegation (`connectionsSeverAccount`, reason `recovery`, through the identity `severConnections` port, best effort after the commit). Deliberate exception: key delegations are not epoch-bound, because delegation status is a public read with no identity lookup; they end by that explicit revocation instead (review 2026-10-23 item 3, provisional; Reviewer ___ / Date ___ / Outcome ___). Recovery files carry no keys, so replacing the reset credential fully retires an old file once any cooling-off window ends.

Handles are permanently nonreassignable under [the name policy](identity-names.md). Permanent claims are not sufficient recovery authorization. Reconstitution after identity deletion additionally requires retained recovery authority, key-generation continuity, live revocation state and a crash-safe restoration protocol. Missing those records must fail closed even if a name certificate or old private key is valid. A backup predating revocation must never revive a grant, and another provider cannot claim the original provider's name namespace without an authenticated migration protocol.

Offline guessing of the recovery answers exposes only a reset credential that works at the live provider and is revoked by the next reissue. Retain the existing explanation of PII entropy and private-passphrase recommendation.
