## Identity and artifacts

The identity is an immutable, canonical lowercase UUIDv4. A free or paid name routes to that UUID and may be certified separately. Recovery must not depend on the current spelling, preferred alias or availability of a name. Signing and encryption keys belong to the UUID; neither answers nor handles generate them.

The two artifacts have separate purposes and contents:

| Artifact | Contents and handling |
| --- | --- |
| Encrypted recovery file | Provider-signed issuer, UUID, random reset credential, original signing private key and separate encryption private key, with bounded warning/version metadata. No handle, alias, assignment identifier or name certificate, including within encoded signed payloads. Keep the complete signed payload inside answer-derived authenticated encryption. |
| Public name certificate | Provider-signed issuer, UUID, exact canonical handle, assignment identifier and issuance time. No private keys, reset credentials or private recovery proof. Download separately; it can be shared as evidence of historical assignment. |

Changing or adding a name does not require a new recovery file. A name certificate is historical issuance evidence, not a current login credential or a permission grant. A certificate supplied with its own untrusted verification key does not establish provider authority.

Preserving a UUID and keychain preserves cryptographic identity. Keeping old contact links operational additionally requires original routing and current grant, expiry, quota, quarantine, collection and key-status records. Private keys alone cannot reconstruct deleted grants, revive revoked permissions or recover missing messages/files. Existing provider OAuth credentials, application consents and passkey private keys are outside this recovery package.

## Recovery wire schema and API

Keep the existing outer `3sln-recovery` envelope version 1 and its Argon2id, normalization, AES-GCM, bounds and every-answer requirements. Independently version its decrypted payload as version 2. The exact parser and cryptographic implementation are `packages/recovery/identity-backup.mjs`.

```js
createIdentityBackup({issuer, entity, keychain, recoveryToken, warning}, authority)
verifyIdentityBackup(backup, authority, {issuer, entity})
validateIdentityBackup(backup)
```

The decrypted shape is `{version:2,issuer,entity,recoveryToken,warning,keychain,proof}`. `entity` is the UUIDv4. The keychain is `{version:1,signing:{kid,privateJWK},encryption:{kid,privateJWK}}`. Original ECDSA P-256 signing identity and its `kid` are adopted from AccountObject; export must not generate a replacement if a signer exists. Encryption uses an independently generated ECDH P-256 key with a different key ID and scalar. Provisioning that key does not establish that existing content uses it or that messaging is end-to-end encrypted. Future encryption use requires its own context-bound KDF and authenticated-encryption protocol.

The proof is `{alg:'ES256',kid,payload,signature}`, where payload is unpadded canonical base64url of the exact bounded JSON backup object before the proof is added. Sign the UTF-8 bytes of `3sln-identity-backup-v2.ES256.<provider-kid>.<payload>`. The proof payload is reversible and contains private keys and the reset token; it must never be published as a public identity certificate. The complete proof, keychain and reset credential remain inside the answer-encrypted file. A generic or UUID-based download filename avoids putting a handle in the recovery artifact's public name.

Reject unknown fields, names embedded in a v2 schema, unsupported versions/algorithms, malformed canonical encoding, invalid UUIDs, incorrect key usage, identical signing/encryption material and private/public scalar-point mismatches. Verify correspondence cryptographically; importing a supplied private JWK alone is not proof that its public coordinates match its scalar. The implementation uses isolated sign/verify correspondence checks for P-256 scalar-point validity, including the encryption key, without publishing those temporary validation signatures or using the encryption key for application signatures.

## Separate name certificate API

```js
createNameAssignment({issuer, entity, handle, assignmentId, issuedAt}, authority)
verifyNameAssignment(certificate, authority, {issuer, entity, handle, assignmentId})
```

The result is `{version:1,type:'3sln-name-assignment',issuer,entity,handle,assignmentId,issuedAt,proof}`. Its proof signs UTF-8 `3sln-name-assignment-v1.ES256.<provider-kid>.<payload>`, where payload contains the canonical public fields only. Signing and verification use a distinct purpose from recovery. Copying a recovery proof into a name certificate fails verification. The creator accepts only the exact public inputs; passing a keychain or reset credential fails rather than silently serializing it.

Certificate handles must already be in the canonical form returned by the shared namespace parser. Lookup accepts supported case/Crockford spelling variants, but certificates retain the exact signed canonical spelling. The assignment identifier binds the retained identity assignment lineage; several name claims for the same UUID may share it. Exact issuer, UUID and handle disambiguate each signed name. A new paid alias receives a separate name certificate and does not modify the recovery payload or the canonical free name. The name certificate does not promise data retention or authorize restoration of a deleted account.

## Provider trust and custody

The provider recovery/name signing private key is independent of user keys and `KEY_ENCRYPTION_KEY`. It never enters either artifact as a private key and must not be derived from the credential-encryption secret. Node development adapters persist their authority with private filesystem permissions across restarts; deployed adapters require explicitly configured stable authority. An absent authority must fail before creating account keys or issuing a recovery credential.

Verify against the independently selected provider's trusted key, never an issuer URL, key URL or bundled authority chosen by the file. The browser may obtain a public authority from the currently selected same-origin provider; this uses that origin's TLS trust and does not protect against provider compromise. Offline verification requires a separately trusted saved public key. File decryption remains independent of server keys, but the current browser workflow's online authority verification and live account recovery require provider availability.

Provider rotation requires retained trusted verification history and an explicit compromise policy; a single configured signer is not a completed rotation system. A retired public key can support historical signature inspection without granting current recovery authority. Configured credentials and local signatures are not evidence of production custody or external conformance.

## Export and retained-account recovery

1. Require the existing limited setup authority, or an owner session under the rules of [active-account reissue](#active-account-reissue-provisional). Warm AccountObject state before export. Idempotently adopt the existing signer and persist a distinct encryption key once under the account gate.
2. Validate signing authority before key creation. Issue a signed UUID/keychain/reset package and commit its random-token hash under identity revision/CAS checks. Do not return a usable package after a failed commit. Cross-object partial work must remain retryable without changing identity keys.
3. Encrypt the package in the isolated first-party recovery document. Retain every-answer local decrypt verification and explicit save acknowledgement before activation. Neither a download click nor an in-memory round trip proves a durable filesystem write.
4. On restore, decrypt and verify exact schema, issuer, trusted provider signature and key correspondence. The server independently checks the full signed v2 package, current UUID and original keys, plus the current reset credential or its active transaction resume credential. Name state is not a verification input to recovery.
5. Compare against retained keys without creating missing keys or replacing current keys during verification. Reject absent accounts, missing key state, altered keys or unavailable authority. Automatic key repair/import and account reconstitution are separate future protocols.
6. On first recovery revoke old password/passkeys and sessions, preserve a transaction-scoped resume hash and its original payload-version requirement, and enter recovering. Resumption preserves newly completed setup. Replacement-file confirmation atomically reactivates the same UUID and removes old resume authority. A consumed token or copied private key alone cannot start another recovery.

Persist a v2-required marker on upgraded accounts. Omitting the proof or presenting a stripped v2 reset token must not invoke the legacy path. An original v1 transaction remains resumable as v1 while its replacement v2 file is prepared; activation enforces v2 for future recoveries. Explicitly recognized legacy v1 files contain a handle and random token, but no portable keys. That old format remains supported only where live account policy permits it; malformed v2 files never downgrade. The unreleased earlier name-bearing v2 candidate is rejected by the current strict schema.

Keep private keys, answers, tokens and decoded recovery payloads out of logs, public UI state, telemetry, URLs and browser persistence. A public handle may be returned beside the recovery content for setup display; it is not part of the downloaded encrypted recovery payload. The provider's stored private-key copy remains encrypted under `KEY_ENCRYPTION_KEY`; losing that key does not prevent offline file decryption, but the current retained-account flow does not repair unreadable provider records automatically.

## Active-account reissue (provisional)

Status: **provisional, implemented locally 2026-10-23, not reviewed, not signed off.** Reviewer ___ / Date ___ / Outcome ___. It closes the gap recorded in [identity portability](../../architecture/identity-portability.md) §10.1: P15 (rotate at every issuance), P14 (a current file at least 7 days old), the mandatory fresh file after an elevated-proof abort (§6.1a, P17) and PORT-4's `recoveryRequired`. No new flag: it is available wherever v2 recovery files are (a configured recovery authority). Code: `IdentityService#reissueRecoveryBegin` / `#reissueRecoveryConfirm` / `#reissueRecoveryCancel*` (`packages/identity/service.mjs`), the account gate `packages/identity/recovery-reissue.mjs`, `TransferOutService#recoveryReissue`; routes `POST /api/auth/recovery/reissue/begin`, `/confirm`, `/cancel`, `/cancel-email`, `/cancel-file`, and the cancel page `/account/recovery/cancel` (`packages/runtime/routes/recovery-reissue.mjs`); tests `tests/recovery-reissue.test.mjs`, the seeded `tests/recovery-reissue-chaos.test.mjs` and `tests/identity-wargame2.test.mjs`.

**Cooling-off window (user decision 2026-10-23 after the identity wargame, provisional; Reviewer ___ / Date ___ / Outcome ___).** The red-team review showed that a stolen password alone became a permanent takeover: step up with the (aged) password, reissue, then immediately `recover()` with the new file, which wiped the owner's passkeys and sessions. The rules (a)–(d) below replace "the previous file stops working at confirmation".

- **(a) Passkey first.** If the account has any passkey, the reissue step-up must be a passkey step-up. A password, however old, never authorizes it. Without a passkey, an aged password still does (accounts with no passkey have nothing stronger).
- **(b) The new file waits.** A reissued file cannot start `recover()` until it is 7 days old (`recovery_not_ready`). This mirrors P14, which already kept it from authorizing a move for 7 days.
- **(c) Cancellable for 7 days.** During the window the reissue can be cancelled from: any session created before the reissue **began** (the owner's earlier devices, including the requesting session itself); the link in the confirmation notice, sent only to an email verified before the reissue began; or the previous file (below). Notices go to every channel (email and push) at begin, at confirm and at cancel. Cancelling restores the previous credential, kid and version (and any forced-reissue marker the reissue consumed), voids the new file and bumps `security`.
  - A cancellation also ends every session created at or after the reissue began, plus the session that staged it and the one that confirmed it (`recoveryPrevious.stagedSessionId`, `confirmedSessionId`), and severs app connections (reason `recovery`): the cancel CAS (like a recovery start) writes a durable `pendingSever` row that is retried at recovery activation, at the next owner view and by a later cancel until the port succeeds; a run clears only the row it ran (matched on `at`), so a newer row waits for its own run. The account side severs connections first, then revokes every remaining key delegation.
- **(d) The previous file is cancel-only, and only after a reissue that is not file-proof.** It may be the stolen one, so during the window it never starts a recovery. After a reissue authorized by a **password** step-up (an account with no passkey) it can cancel the pending reissue (`recovery_reissue_pending`; `/cancel-file`, after full v2 verification against its bound kid) and gets its full authority back only through that cancellation; otherwise a password thief could lock a password-only owner out. After a **file-proof** reissue it can neither recover nor cancel (`recovery_reissue_locked`, `reissue_cancel_not_allowed`): that reissue may be retiring a leaked file, so only earlier sessions and devices and the current pre-reissue email can cancel it. Coordinator decision 2026-10-23, provisional; Reviewer ___ / Date ___ / Outcome ___.
  - **File-proof** (independent review 2026-10-23, R1(i), provisional; Reviewer ___ / Date ___ / Outcome ___): the step-up was a passkey **enrolled before the previous file was issued**, and **no channel-removing event happened at all in the 30 days before the begin**, whatever its order relative to the passkey (re-verification 2026-10-23, V1; the first version only counted events after the passkey's enrolment). Channel-removing events are recorded in an uncapped monotonic `account.lastChannelRemovalAt`, which the check reads (final check 2026-10-23, V2: a capped list that kept its earliest entries let filler events push a later removal out); `account.authorityEvents` keeps only the newest 16 for display. They are: an email change or removal, revoking other sessions, a session-cap eviction (signing in an 11th session evicts a live one) and a passkey removal. The check is evaluated at the begin and again at confirmation, both anchored at the begin time, so an event inside the lookback at the begin still counts if it ages out before confirmation. Anything else takes the password branch. This closes the review's takeover: a password thief who enrols their own passkey, swaps the email, waits and revokes the owner's sessions makes a reissue the owner's file can still cancel. `recoveryPrevious.fileLocked` records the outcome at confirmation.

Representation: confirmation keeps `account.recoveryPrevious` = {hash, issuedAt, kid, version, marker, reissuedAt, preparedAt, until, newKid, cancelHash, credential, fileLocked} beside the new current credential. `pendingReissue(account, now)` is the live window. The window ends by time (the record is ignored, then dropped by the next recovery or reissue), or by cancellation. A recovery started after the window (with the new file) drops it.

**Edge cases.**

- **No passkey and no email.** The reissue needs an aged password. Cancel channels are the sessions that predate it and the previous file. The owner who still has the file is protected; one who has lost both the file and every earlier session cannot cancel, which is the same position as an owner without a file today.
- **Email changed before the reissue.** A verified email that is replaced or removed is kept for 30 days (review R1(iii); 7 days in the first version; stored one hour longer so a confirmation up to 30 minutes after a begin still finds it) in `account.previousEmails` (up to 8 within retention; a further change is refused with `email_change_limited` rather than dropping one, so no swap sequence can push the owner's address out). Reissue notices at begin, confirm and cancel go to the current email and to every email replaced in the 30 days before the begin (confirmation notices are anchored at the begin). Because a replacement is itself a channel-removing event in the same 30-day lookback, a reissue that sees a replaced address is never file-proof, and one begun after the lookback finds neither. After a password-branch reissue the cancel link goes to each of them that was verified before the reissue began; after a file-proof reissue it goes only to the current pre-reissue email, and replaced addresses get the notice only (review R2: a replaced address may be the compromised one the owner retired). So an attacker who swaps the email (which needs only a recent sign-in) and then reissues does not silence the owner's address. An email verified after the reissue began gets the notice but no cancel link; one replaced more than 30 days earlier gets nothing.
- **Security notices** (review R1(ii), V1). Adding or removing a passkey, changing or removing the email, signing out other devices, a session-cap eviction and setting a password during a recovery notify the current email, every email replaced in the last 30 days and push, each saying how to respond (`IdentityService#queueNotice`, sent after the record's commit through the existing security-alert templates and push security-notice events). Notices are coalesced per account and type, and only for repeats by the **same** acting session or credential within 10 minutes; a different actor is always notified at once (final check N1). A coalesced count is sent as a trailing notice at the account's next write or owner view after the window (`account.noticeLog`). Known limit: there is no identity-side alarm, so if nothing touches the account after the window the trailing count waits; the first event of every actor is never delayed. Passkey enrolment begin is rate limited per account and network. Coordinator decision 2026-10-23, provisional; Reviewer ___ / Date ___ / Outcome ___.
- **Reissue during an active recovery.** Impossible: a recovering account has no owner sessions, and a staged reissue is discarded when a recovery starts. A recovery cannot start during a window with either file, so a window and a recovery never overlap; a recovery started after the window drops `recoveryPrevious`.
- **One window at a time.** A new begin is refused (`recovery_reissue_pending`) while a window is open. Otherwise a second reissue would push the trusted previous file out of the window. The owner who wants a different file cancels first.
- **Authority epoch (`aep`).** A reissue and its cancellation do not raise `aep`; no one inherits the identity at that moment. The recovery that eventually uses a file raises it at activation, as before. Organization governance holds therefore start only when a file is actually used.
- **P15 rotation.** Begin rotates away from the current file's kid and binds both kids, as before. Cancellation runs in the account single writer: it rotates the signing key away from the voided file's kid (so whoever minted it holds no current signing key) and keeps the restored file's kid bound, so the previous file restores again. An ordinary rotation during the window clears the binding, as it always did, so the previous file then no longer restores (known residual below). The encryption key is never rotated: a voided file still disclosed it (known residual).
- **OAuth grants.** `federationEpoch` hashes the current recovery credential, so a confirmation revokes every grant. Cancellation restores the old hash, which would revive grants from before the reissue; it therefore also raises `account.federationGeneration`, a monotonic component of the epoch. No grant from before or during the window survives a cancellation.
- **Transfer-out.** Confirmation still cancels a pending or held move. During the window the current credential is younger than 7 days, so P14 refuses any new move. A cancellation bumps `security`, so the 7-day look-back refuses a move for another 7 days even though the restored file is old.
- **Forced paths.** An elevated-abort or transfer-in reissue has no previous credential: the window still applies to the new file; cancellation leaves no current file and re-arms the forced marker. (a) applies to forced reissues too.
- **P17.** The contest check compares the credential that confirmed the step-up (a passkey id or `password`), not the one the session signed in with (wargame 2026-10-23).
- **Deletion and custody.** Begin and confirm keep their refusals. Cancellation is allowed during a scheduled deletion (it only restores a credential) and refused once the account is purging or deleted.

**Trade-off of V1 (recorded):** an owner who changes the email (or signs out other devices, removes a passkey, or is evicted at the session cap) and then reissues with an old passkey within 30 days gets the password branch, so the previous file and the replaced address can cancel. If those are the compromised ones (review R2's scenario), an attacker can cancel the reissue and recover with the leaked file. V1 accepts this to keep the owner's channels alive against a thief who removes them; an owner retiring a leaked file should wait out the lookback after changing the email, or rely on support. Reviewer ___ / Date ___ / Outcome ___.

**Safer variants considered.** As first implemented, (d) let the holder of a leaked file cancel the owner's reissue and recover at once. Two alternatives were weighed: (1) on a passkey-authorized reissue, deny the previous file the cancel right (sessions, devices and email only); (2) send a file cancellation of a passkey-authorized reissue to support (a P17-style contest). **Variant (1) was chosen** (coordinator decision 2026-10-23, provisional; Reviewer ___ / Date ___ / Outcome ___), and the password branch keeps the file's cancel right. Its cost: an owner whose passkey device was taken and who has neither an earlier session nor a pre-reissue email cannot cancel a reissue made with that device. Variant (2) was not adopted because it adds a support dependency to every leaked-file case.

**Who may reissue.**

- A signed-in owner of an active account, with a step-up in the last 5 minutes made with a credential enrolled at least 7 days earlier: a passkey when the account has one, otherwise the password (P18, P19, rule (a)). The step-up records which credential confirmed it; a password's enrolment time is `passwordSetAt`, and a record without one fails closed. When an aged credential exists but a newer one was used, the console asks again.
- A forced path, armed on the identity record, waives the credential age, but only for a credential enrolled no later than the moment it was armed. A credential added afterwards still waits 7 days. A fresh step-up is still required. The forced paths are:
  - after an elevated-proof abort, which invalidates the current file and arms the reissue in the same action;
  - at PORT-4 activation, where the destination's recovery port arms it. The file is encrypted in the owner's browser, so activation keeps reporting `recoveryRequired` until the owner downloads.
- Within 30 days after an elevated-proof abort, a reissue by any credential other than the one that aborted is contested and refused (P17). Support then decides.

**What it does.** It runs in two phases, so an interrupted reissue never leaves the owner without a working file.

1. **Begin.** The account single writer applies the refusals below. It then rotates the signing key with a continuity statement (P15). The kids rotated away are those of the current file, of an abandoned staged file and of an invalidated file. With none recorded it always rotates, except for a transfer-in arrival, whose key was already rotated at activation (P11). The outgoing and the new kid are merged into the recovery binding (`keys.mjs`). So the current file, now holding a retired key, keeps restoring until phase 2. The new file is **staged**: bound to the requesting session for 30 minutes, not yet current. A new begin replaces an earlier staged file, which never becomes current. Every channel is notified.
2. **Confirm.** This runs after the browser has encrypted, saved and test-unlocked the file. The account gate runs again. It also checks that the staged kids still restore: an ordinary rotation since phase 1 clears the binding, so the owner must start again. A pending or held transfer-out is cancelled (below). Then one identity CAS makes the staged credential current and opens the window: `recoveryIssuedAt = now` (so P14's 7 days start again), the previous credential moves to `recoveryPrevious`, the file's kid is bound, any forced marker is cleared and `security` is bumped.
3. After the commit, notices go to the verified email (with the cancel link when that email predates the reissue) and to every push subscription. Acceptance is not delivery. The audit entry is visible on every signed-in session, and the console shows the window with a cancel button on earlier devices.
4. **Cancel** (any time in the window, by the channels in (c)): the account writer rotates away from the voided kid, then one identity CAS restores the previous credential, raises `federationGeneration`, bumps `security` and notifies every channel.

**Where it cannot run.**

- **Deletion.** It is refused while a deletion is scheduled or executing, after the purge has started, and after the tombstone. A deletion requested after a reissue's gate is ordered after that reissue.
- **A pending transfer-out is cancelled, not refused.** The move was authorized by the file the reissue replaces. The new file is under 7 days old (P14). A move begun in the window between the gate and the identity commit is still cancelled by the transfer-out engine's own check: the epoch and the credential reference changed (`cancelReason`). A new move then also hits the 7-day security look-back at request time. So a reissue can never be used to start or speed up a move, and P14 cannot be dodged. Cancelling is the safe direction. It is consistent with the spec §6.1 rule that recovery and credential changes cancel a move. Refusing would instead stop an owner from retiring a file that someone else is using to move the identity.
- **A contested transfer or the support lock: refused.** Support's "allow" needs the requester to still hold the current file, so a reissue here would be the second self-resolution that P17 forbids.
- **Moved or arriving identities: refused** by the custody fence.
- **An open window: refused** (above).

**Concurrency.** Begin, confirm and cancel are linearized in the account single writer against transfer-out steps and commits, deletion, and ordinary rotations. The identity CAS trails them.

- An identity CAS that loses returns no file. The rotation that preceded it is harmless, because the binding merge keeps the current file restoring (review M1).
- There is one staged slot per account and at most one window.
- A recovery started with the current file before a confirmation discards the staged file and any forced marker. Its sessions end, so no confirmation follows.
- A cancellation whose identity CAS loses retries against the same window (`reissuedAt`). If it never lands, its rotation is still harmless: `rotateForRecovery` merges the outgoing (new file's) kid into the recovery binding, so the still-current new file keeps restoring (review item 7; tested). Making rotation and identity commit one step would need a cross-store transaction; not done.

**Known residuals (unsigned).**

- After a password-authorized reissue (accounts with no passkey) a holder of a leaked previous file can still cancel it and recover; after a passkey-authorized one, an owner who lost the passkey device and has no earlier session or pre-reissue email cannot cancel (see "Safer variants considered").
- Replaced emails are retained for 30 days for this purpose (`previousEmails`), which the privacy notes must mention.
- An owner who enrolled their only passkey after the current file was issued gets the password branch for a passkey reissue: the previous file can cancel it.
- A password-only attacker on an account without a passkey still obtains, in the voided file, the encryption private key (never rotated) and a signing key that is retired at cancellation.
- An abandoned staged file holds the current signing key until the next issuance rotates it away. It was only ever delivered to the stepped-up owner session.
- A transfer cancelled by a confirmation whose identity CAS then lost stays cancelled. That is the safe direction.
- The owner's "reissue" choice after a dispute (spec §6.2) invalidates the file without arming the forced path. An owner without an aged credential therefore has no current file until one ages.
- Notices reach emails replaced or removed in the last 30 days (`previousEmails`), not older ones.
- The restorability check runs in the account gate, not atomically with the identity commit. An internal, admin-only rotation or revocation landing between the two could commit a file that does not restore, or (during a window) unbind the previous file. It is not reachable through any route.
- When the key history is full of referenced keys, issuance skips the rotation (the known P15 edge). That is audited but not shown to the owner; a cancellation that cannot rotate is audited the same way.
- A begin during a pending move rotates the signing key. If that reissue is abandoned, the move's statement may no longer verify against the current key, so the move fails. That is the safe direction.
- The encryption key is never rotated, so superseded files keep the current encryption private key. P15 covers signing keys only; this needs its own decision.

## Return, compromise and missing state

For retained accounts, returning restores access to the same UUID and keys. Existing active unexpired contact links can resume once the account becomes active; expired, revoked, exhausted or absent grants remain denied. Recovery is not full compromise remediation: it preserves identity keys, email-login settings and resource permissions. It does **not** preserve OAuth app authorizations: the grant epoch (`federationEpoch`, `packages/runtime/federation.mjs`) hashes the current recovery credential, so starting a recovery, confirming a reissue or cancelling one revokes every app family, code and token, and apps must be authorized again (the safe direction; reconciled with the code 2026-10-23). A monotonic `federationGeneration` on the identity record also feeds the epoch; it rises when grants must end without a credential change (reissue cancellation, suspension), so a restored credential or a reopened account never revives an older grant. MCP grants record the same app-grant epoch at approval and are refused on verify, execute, exchange and refresh once it changes (`packages/runtime/grant-epoch.mjs`; legacy grants fail closed). Recovery start and reissue cancellation also sever every app connection (integrations §7) and revoke every key delegation (`connectionsSeverAccount`, reason `recovery`, through the identity `severConnections` port, best effort after the commit). Deliberate exception: key delegations are not epoch-bound, because delegation status is a public read with no identity lookup; they end by that explicit revocation instead (review 2026-10-23 item 3, provisional; Reviewer ___ / Date ___ / Outcome ___). Replacing the reset credential cannot erase a copied private key. Key rotation/retirement requires an explicit future flow and must prevent rollback from old files.

Handles are permanently nonreassignable under [the name policy](identity-names.md). Permanent claims are not sufficient recovery authorization. Reconstitution after identity deletion additionally requires retained recovery authority, key-generation continuity, live revocation state and a crash-safe restoration protocol. Missing those records must fail closed even if a name certificate or old private key is valid. A backup predating revocation must never revive a grant, and another provider cannot claim the original provider's name namespace without an authenticated migration protocol.

Offline guessing of the recovery answers now exposes durable private key material as well as a reset credential. Retain the existing explanation of PII entropy and private-passphrase recommendation. Token revocation cannot revoke decrypted copies of keys.
