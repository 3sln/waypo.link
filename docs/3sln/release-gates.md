# 3sln.me security policy and release gates

> **Group:** 3sln.me reference service
>
> **Status:** proposed. The runnable local service is not a production identity provider until these gates are implemented and reviewed. Production release remains disabled.
>
> **Covers:** 3sln.me's reference-host presentation and framing policy, its account abuse controls, audit and operational controls, and the verification required before a public beta.
>
> **Does not cover:** the interoperable Bindle security model that every provider follows, which is [Bindle security](../spec/security.md). This document applies that model to one host and adds host policy; another provider may choose differently.

## Reference-host presentation and framing (3sln.me policy)

This section is 3sln.me reference-host and `@3sln/bindle` SDK policy, not Bindle interop. It was moved out of [auth](../spec/auth.md) and [protocol](../spec/protocol.md) on the user's 2026-10-14 direction that the Bindle specification say nothing about UI. Other providers may choose differently. Design: [adaptive app sign-in](../architecture/adaptive-app-sign-in.md).

- **Handle entry.** The `@3sln/bindle` sign-in element shows the framework brand, an editable handle and a visual `@3sln.me` suffix until `@` is typed; submission resolves the complete handle, and the element names the resolved provider host before navigating.
- **Framing.** Login, account management, consent, recovery and console pages send `frame-ancestors 'none'` and `X-Frame-Options: DENY`. The only framed provider documents are the island documents at the root (`/?client=…`) of a dedicated cookieless embed origin that serves nothing but islands (the provider-private sub-resources `/embed/assets/*`, `/embed/api/*` and `/embed/sw.js`; every other path is 404; never the console origin), with `frame-ancestors` set to the exact registered origins of the `client_id`, display-only authority, no cookies read, and every sensitive action escalated to a top-level popup. Islands never delegate to FedCM. Consent never happens in a frame.
- **Popups.** Authorization pages use `Cross-Origin-Opener-Policy: same-origin`, a static cookie-independent entry document, controls inert until visible and focused for 600 ms, and no default focus on approve. Completion is a top-level redirect to the registered redirect URI. The one exception is the single static entry document for popups opened by the embed frame, served without COOP so the opener survives; it refuses to run framed or sandboxed, shows no account state until an opener-key handshake succeeds, otherwise replaces itself with the `COOP: same-origin` authorization page, and posts only a key-bound claim and the code to the embed origin with an exact `targetOrigin`.
- **Islands** ([embed islands](../architecture/embed-islands.md)). Only allowlisted parts (`avatar`, `account-switcher`, `sign-in`) load; sizes are fixed or set by the embedder, never by state; islands send no state-dependent messages, sizes, focus or error signals; avatar responses are re-encoded rasters with `Cross-Origin-Resource-Policy: same-origin`, no CORS and `no-store`; the partitioned service worker never caches API responses; `/embed/api/*` requires an exact embed `Origin` on non-GET requests and on any GET that carries one.
- **FedCM cookie.** The only `SameSite=None` provider cookie is `__Secure-bindle_fedcm` (`Path=/fedcm/api/`, HttpOnly, not partitioned), holding session-class FedCM-purpose capabilities (rotated on every install, revoked with their sessions) rather than console session tokens; every `/fedcm/api/*` handler requires `Sec-Fetch-Dest: webidentity` before reading cookies, and FedCM login/continuation pages live outside that path and authenticate with the Strict cookies. Per-account login cookies stay `SameSite=Strict`.
- **Browser app credentials.** Persistent browser refresh tokens are issued only DPoP-bound. Embed credentials are delivered only to the embed frame, bound to its non-extractable key, never reach the app and never authorize RPC.

Verification before public beta: framing refusal on every non-embed route; embed `frame-ancestors` under allowed, unregistered and nested parents; FedCM endpoints refuse non-`webidentity` requests with identical timing; embed restore fails with another key, client or site; refresh reuse revokes the client session and its embed token; R1 one-click sign-in for an already signed-in user in Chromium (FedCM and popup), Firefox and WebKit. Islands: size, load-count, timing and focus probes identical across account states; popover close matrix; leader failover across tabs; avatar hotlinking refused from other origins and as a top-level or `<img>` load from the embedder.

## Account abuse controls (3sln.me policy, provisional 2026-10-23)

From the identity and federation wargame of 2026-10-23; Reviewer ___ / Date ___ / Outcome ___. Anything keyed to a victim (handle, mailbox, account, owner shard) is charged only after the caller has passed a CAPTCHA or proved a credential, so unauthenticated traffic cannot lock a person out. Per-network windows run first. Sign-in charges the handle window only for completed, failed password checks; passkey sign-in begin stores nothing. Email sign-in charges a mailbox window for every address alike and answers in constant time. A pending setup token buys at most 5 password sets and 5 recovery downloads behind the limiter. Anonymous app authorization requests have their own per-caller and per-shard bounds and join the owner's bound only at the owner step; incremental DPoP proofs are recorded only once a code bound to that key exists, in per-key partitions. The admin console accepts only a passkey step-up; boot challenges are per-caller rows bound to a nonce cookie, and boot password attempts have principal and global ceilings. A stolen password cannot replace the recovery file of an account with a passkey, and any reissued file waits 7 days before it can recover, during which earlier devices, the pre-existing email and the previous file can cancel it ([recovery identity](accounts/recovery-identity.md#active-account-reissue-provisional)). Evidence: `tests/identity-wargame2.test.mjs`, `tests/federation-wargame2.test.mjs`, `tests/boot-admin.test.mjs`. Local engine and Node evidence only; no production verification is claimed.

## Audit and operational controls

Record account and grant changes, credential enrollment/removal, session transitions, connector lifecycle and denied privilege expansions. Audit events omit raw tokens, challenges, credentials, preference values, file contents and unnecessary email addresses. Users can inspect relevant events; production retention and deletion policies need explicit sign-off. Separate security telemetry from user exportable event history. Encrypt secrets/backups, test restore and key rotation, and document recovery from provider compromise. No production email, integration credentials or deployment changes are necessary for the local prototype.

| Passkeys | Wrong origin/RP/challenge/type/signature; replay; missing verification; account binding; enrollment/deletion authorization; synced counter handling. |
| Authorization | Cross-user/client/resource/method rejection; assignment removal immediate; expansion consent; immutable revision checks; optional fragment privacy; @profile restrictions. |
| RPC | Payload-changing idempotency collision; cross-principal tx IDs; revocation on replay; race between revoke and mutation; bounded resource exhaustion. |
| CBOR RPC ([cbor](../spec/cbor.md), provisional 2026-10-29) | Every decoder refusal of cbor §5 on every RPC route (Bearer, DPoP, `BindleEntity`, relation tokens, brokered `rpc_endpoint`); 415 for JSON and 413 on encoded size before decoding; no route-generated JSON body on the RPC path; integers at 2^53 ± 1 and 2^64 ± 1 through every built-in contract that takes integers, with no `Number()` coercion between decode and use; `x-type` bytes refused where text is expected and the reverse; a bounded seeded fuzz run in `npm test` plus a longer fuzz run before release; journal and object-URL resets (`format: "cbor1"`) observed on both hosts. |

| Consent | User tests accurately identifying recipients, field data, resource powers, shared-fragment consequences and revocation limits; keyboard/screen-reader flow and cancellation. |

No runtime assertion exists, because Worker test fixtures combine the flag with `.example` origins; verify the production `wrangler.jsonc` value (`"false"`) before release. |
| Operations | No secret leakage; connector disconnect; encrypted backup restore; rate-limit abuse and enumeration review; dependency/security review. |
| Passwords removed (sign-in and intents spike §6.3, provisional) | No password route is reachable on the deployed Worker or Node host (`/api/auth/login/password` and the pending-password route answer 404; sign-up, step-up, linked approval and transfer enrollment refuse a password). Password-derived authority is refused at use time: a password session, any session approved from one, an activation session of a record that still carries password fields, an approved-but-unconsumed request whose approver is such a session, and an older app lineage approved from one. Evidence that the `passwords-retired-v1` reset completed on each host: the Node boot sweep's marker in the identity metadata, and the Worker scheduler's marker (cron trigger and lifecycle alarm) in the `LifecycleScheduler` object storage, with no `passwordHash` left in either identity store. |
| Sign-in email states (spike §3.2, SI-23) | `unverified` → `verified` → `sign-in` transitions only as specified; an unverified entry never holds the uniqueness claim and expires after 24 h; at most three verified addresses and one notice address; every verified and sign-in address receives security notices (sign-in email changes, passkey changes, identity-move begin, contest and restart notices with their own dispute tokens, owner-deletion and lifecycle notices); choosing another notice address notifies the previous and the new one. |
| Sign-in method removal (spike §6.4, provisional) | For sign-in emails and passkeys alike: RM-1 (the recovery file and one working method always remain); RM-2 Tier A (a method under 7 days old undone at once with a fresh assertion from an established passkey other than the target); RM-3 (a recent method an email session added undone from a fresh ordinary `email` session on an established sign-in email, never from an `email-cross-device` session, and nothing added through a passkey, setup or recovery); Tier B (an established method) refused with `removal_unavailable` until file proof and the notified delay exist. Includes the case of a session holding a freshly added passkey that tries to remove the owner's established passkeys. An email-only account may add a passkey from a fresh email session (SI-4, Q8), which records `addedBy: email` and notifies every channel. |
| Provisional passkeys (spike N2; coordinator decision 2026-10-29 after the P3 security review H1, provisional) | A passkey added under email authority (any email session, or the setup of an account created from a create-account link) is provisional for 24 h on the deployed host: it signs in at once; the session it creates (`passkey-provisional`) and any step-up attempt with it (refused, `passkey_provisional`) satisfy no authority check: `recent()`, `privileged()` (account deletion, data export, DX-6 email removal), method removal, recovery-file reissue, revoking other sessions, turning sign-in on for another address, LA-7, federation `auth_time` and identity-move evidence. Includes the earlier step-up gap (email session → passkey → step-up → deletion or export). |
| Sign-in continuation (spike §2.2, SI-8) | One tab-local record, at most one hour after capture and never extended; resumed once by the shared sign-in step; discarded on recovery completion, sign-out, signing out the tab's account and account switch; return targets limited to `/i` and the anchored authorization path. |
| Cross-device email link (spike §4, §5; `EMAIL_FLOW_V2`, provisional) | EL-1 on the deployed host: a link opened in another browser, a forwarded link and a link a scanner opened never yield a session there; only the original tab with its secret (plus the code on the copy-code path) or the same-browser "sign in here instead" redeems. Same-browser approval and the BroadcastChannel wake-up in Chromium, Firefox and WebKit (WebKit is not covered by the local browser tests); the in-app-browser case (no marker) falls back to the code. Code attempts lock at 5; the per-prefix (20 per hour) and global code budgets, and Turnstile once the global one is spent; every attempt is reserved before the comparison, so parallel guesses against the deployed Durable Object store never exceed any limit. Resend charges the mailbox windows shared with start (at most 12 mails per address per 6 hours, starts and resends together). The helper document is reachable only at `/email/link` (its static path answers 404). The account cap is checked before redemption consumes anything, and a refused sign-in sends no notice. Uniform start: every branch creates a flow and answers the same shape; timing and response-size parity measured on the deployed Worker (local tests compare synchronous work and shard reads only: a miss reads a random account key; residual CPU and latency differences remain). EL-6 races (sign-in turned off, address removed, recovery or a passkey change between start and redeem) fail generically. The `__Host-bindle_email_flow` cookie attributes on HTTPS. ## Signaling (3sln.me policy, provisional 2026-10-28)

`SIGNALING_ENABLED` stays off in production until all of these hold:
- **Owner pages.** Approving a session handler (signaling §20.1.4), creating and activating a pairing (§5.8) and designating a service organization (§4.3) happen only on provider pages that show the required disclosures. The JSON owner routes are adapters for those pages and are not enough on their own. *Status 2026-10-28: implemented locally (console view `signaling`, single-use armed reviews); organization approvals and pairings through the owner interface, the app-request pairing page and the M4 confirmation page remain.*
- **Client sessions.** Revoking a device-authorization client session runs the §14.2 narrowing (`signalingClientSessionRevoked` is wired), before any enrolment page offers pairings.
- **Data profile.** The `data` profile has a cost row and a per-owner budget confirmed against provider usage (§3.5); hosted relay issuance stays refused until the spend authority enforces a per-owner byte cap (§16.7).
  *Status 2026-10-28: the per-person aggregate `data` budget is 256 KiB per hour, the same on every plan, as an abuse guard (owner-approved 2026-10-28; DEVLOG, 2026-10-28, "Owner approvals and directions (in session)"), with the pairing sub-budget at half; enforced and tested at the engine level (`packages/signaling/sessions.mjs` `BOUNDS.dataBytes`). At that budget every paid plan holds the 50% worst-case margin floor without relay (Paid 60.5%); Paid with its whole relay allowance as well is 48.5%, recorded as a `todo` in `tests/cost-model-margins.test.mjs` against the relay byte cap above ([unit economics](../architecture/unit-economics.md) "Relayed signaling `data` bytes"). The request prices are not rechecked against a primary source, and nothing is confirmed against provider usage.*
- **Organizations and service entities.** Signaling budgets for organization and service entities (pending and connected capacity, invite windows and the `data` budget) are tiered by an organization plan, still to be defined, and rate-limited, before `SIGNALING_ENABLED` covers organizations (owner-approved direction 2026-10-28). *Status 2026-10-28: no organization plan or org-tiered budget exists; nothing is implemented.*
- **Conformance.** The peer conformance suite is rewritten from the revision 3.2 text (Appendix C.5 step 6) and passes in strict mode.

## Messaging invitations (3sln.me policy, provisional 2026-10-28)

Bindle Messaging invitations and credential-less first contact (contacts phase 3, implemented locally behind default-off flags) are not offered publicly, and the same-host-only verification rule (CL-24) is not relaxed, until all of these hold:
- **Fetch bounds.** Author-verification fetches are bounded per author issuer and globally, their results (failures included) are cached for at least the status-cache time, and at most one directory fetch and one status fetch start per request ([messaging §7.4](../spec/extensions/messaging.md#74-edge-credential-index-and-first-contact-budgets)). Today verification is a local directory read for same-host authors only; none of these bounds is implemented.
- **Shared budgets.** The per-source and per-owner first-contact budgets and the per-invitation and verification limiters are shared across the instance, not kept in memory per isolate or per mailbox object as they are today. The Node adapter's source is the socket address unless an operator configures a trusted proxy header.
- **Public links.** Multi-use or public invitation links do not ship until both items above hold.
