# Bindle protocol v0 — normative draft

Bindle v0 is an open specification draft, not a deployed interoperability standard. Example canonical URLs under `https://spec.bindle.example/` are placeholders, not live authorities. MUST/SHOULD/MAY express draft requirements. The [OAuth and RPC wire profile](federation-implementation.md) describes the current runtime. The [contract registry](/artefacts/contracts/) links the published draft JSON definitions and a [machine-readable index](/artefacts/contracts/index.json). Canonical contract identifiers return those JSON definitions directly; publication does not imply external-provider compatibility.

## 1. Model and custody

An **entity** is an individual or, later, an organization/team with its own authority and policy. A **provider** operates authentication, preferences, resource adapters and grants for entities. An **application** requests grants. A **fragment** is a public, versioned description of preference fields. A **resource** is an entity-owned capability implementing named contracts. A **contract** defines method names, argument/result schemas, semantics and required authorization.

Entity, application, resource, fragment and contract identifiers are absolute HTTPS URLs. Opaque identifiers are allowed in URL paths. Display handles and emails are aliases, never durable entity identifiers or proof of ownership. Changing aliases MUST NOT change entity identity. Named resource aliases such as `@profile` resolve only within the authenticated entity and MUST NOT override authorization.

Self-hosting means implementing the public protocol without depending on 3sln.me. Hosted custody is delegated custody: a provider can see unencrypted stored preferences and connector credentials. Neither TLS nor OAuth provides end-to-end encryption. Export MUST include preferences, resource metadata and grant history in documented formats; connector secrets require an explicit encrypted export or reauthorization, and grants/tokens MUST NOT migrate automatically. Domain/key continuity and cross-provider identity migration remain a future specification; a v0 export MUST NOT imply portable identity.

## 2. Discovery and login

This specification defines no presentation beyond the security disclosures it lists (such as showing the resolved host and the consent details in §3); how a client collects a handle (for example a default host for unqualified input) is presentation. Every host receives identical protocol treatment. A client MUST parse a single nonempty local part and DNS host, reject URI userinfo, paths, ports and control characters, and display the resolved host before continuing. Domain names use platform IDNA normalization; local parts are preserved and interpreted by the provider. Email case folding MUST NOT be generalized to arbitrary providers.

For `alice@example.org`, fetch `https://example.org/.well-known/bindle/manifest.json`; send `alice@example.org` later as `identity` in the bounded authorization-request POST. **Do not fetch `https://alice@example.org/...`: this is URL userinfo, not a user-scoped host.** Discovery is host-level and MUST NOT enumerate individual existence. Manifest fetches use no cookies or bearer tokens, require HTTPS and JSON, enforce bounded size/time, and reject cross-origin redirects. Server-side fetching additionally blocks private, loopback and link-local targets and revalidates every DNS resolution and redirect. Development localhost is an explicit development-only exception.

V0 requires endpoint URLs on the issuer origin and issuer equality with the requested HTTPS origin; this includes every `endpoint` option of an extension declaration, except the one option that core names (the embedded-components `embed_origin`, below). An `audience` endpoint option MUST also differ from every other audience endpoint in the manifest, and public endpoints, such as a shared key set, MAY share a URL ([extensions §2.4](extensions.md#24-options)). **AMD-C8 — proposed (approved provisionally 2026-10-20):** only the brokered-resources extension permits provider-validated integration-origin endpoints for consumer RPC and provider events under [integrations](integrations.md); this does not delegate issuer discovery, authorization or token endpoints. Providers SHOULD also publish standard OAuth authorization server and protected resource metadata. Clients MUST reject unsupported manifest versions and inconsistent issuer/endpoint metadata.

**Extension declarations (extensions revision 3.2; draft, unimplemented, unsigned).** This text replaces the `features` and `profiles` containers and AMD-C6, pending owner sign-off. The local code still emits the revision 2 shape (`features` keys and slot declarations) behind its flags. Beyond the required members above, a provider declares which optional parts it implements, so clients never have to probe. There are two kinds of declaration, and the absence of a declaration means the documented default:

- OAuth-registered capabilities stay flat, under their registered names, so generic OAuth tooling reads them: `revocation_endpoint` ([RFC 7009](https://www.rfc-editor.org/rfc/rfc7009.html); absent: the client can only clear its own state on sign-out), `dpop_signing_alg_values_supported` ([RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html); absent: no sender-constrained tokens, so a browser client keeps refresh tokens in memory only, [auth](auth.md#token-lifetime-and-client-sessions)), and `grant_types_supported` (a provider that issues refresh tokens MUST list `refresh_token`; Bindle clients assume no refresh when it is absent). Persistent DPoP binding of a browser refresh token also needs the authorization-entry extension, whose entry carries the client's `dpopJkt`. The Bindle member `login_presentation` is required and lists `redirect` and optionally `popup`.
- Everything else optional to implement is an **extension**, whoever publishes it. The `extensions` array holds `{spec, options}` entries as defined in [extensions §2](extensions.md#2-extension-declarations). The spec URL is the extension's identity and is versioned in its last path segment. `options` is validated against the options schema in the extension's descriptor, which a client holds for every extension it implements and never fetches to process a declaration. A provider declares at most one version of an extension: an incompatible change is a new spec URL, declared instead of the old one, and entries for two versions of one line are all treated as absent. There is no `features` or `profiles` member: rev 3 clients ignore both.

**Pending owner sign-off (extensions EXT3-21).** The areas in the table below, including intents, integrations (hub connectivity) and events, which the owner named as core Bindle, are read here as **Bindle-owned extensions**: specified by Bindle and kept in the core document set, but optional to implement and declared in `extensions`. The mandatory protocol stays the conformance floor below. This reading is a coordinator proposal ([extensions §1](extensions.md#1-model)).

The `contracts` member lists every contract any built-in resource of the provider implements ([extensions §5.2](extensions.md#52-built-ins)).

Other specifications define further extensions; [extensions §2.8](extensions.md#28-what-replaces-features-and-profiles) maps every former feature and profile identifier. Third parties publish extensions under their own spec URLs. An extension cannot change core processing: it cannot relax the issuer-origin rule for core endpoints, alter consent, grant, token or RPC semantics, or authorize anything by itself. The only exceptions are those this specification names by extension: brokered resources (§4, AMD-C8) and the component-origin envelope in [auth](auth.md#presentation-transports-and-key-binding) for the Bindle-owned embedded-components extension (`…/embedded-components/v1`, placeholder; provisional, [extensions §2.7](extensions.md#27-extensions-cannot-change-core), §13 Q5). Its content is the [components profile](../profiles/components-v1.md), pending republication. The component origin is the origin of that extension's declared `embed_origin` option, which need not be on the issuer origin and is authoritative because the issuer's own manifest declares it. Non-endpoint URL options are opaque identifiers: clients never send requests to them unless the extension's spec explicitly says so and the URL is on the issuer origin, and such origins never receive the client's PKCE verifier, tokens or keys.

**Processing rules.** The manifest MUST be [I-JSON](https://www.rfc-editor.org/rfc/rfc7493.html) (no duplicate member names) within the 64 KiB manifest bound. `extensions` has at most 48 entries of at most 4 KiB each when serialized. Entries for extensions a client does not implement and entries with an invalid `spec` are ignored. Two or more entries with the same `spec` are all treated as absent. Two or more entries for versions of one line are also all treated as absent. **Prerequisites.** There is no generic dependency member: an extension that depends on another says so in its own spec. A processor of the dependent extension checks only, without recursion, that exactly one entry with the prerequisite's exact `spec` is present in the same manifest, and it need not implement the prerequisite. If the check fails, the dependent extension is treated as absent. Unknown members are ignored. A known extension whose options fail validation is treated as absent; it does not invalidate the manifest, and the required members above still fail closed. A declaration is a claim, not proof: a client that sees a declared extension fail in a way that shows it is not implemented (for example HTTP 404, 405 or 501 from its endpoint) treats it as absent for that issuer until the page or process restarts, never persists that downgrade, and treats network and 5xx failures as retryable errors, not absence. Values from one issuer's manifest apply only to operations bound to that issuer and are never combined with another issuer's declarations. A client MAY cache a validated manifest for at most its HTTP freshness lifetime, capped at one hour, and uses one manifest snapshot from the start of an authorization to its code exchange.

**Conformance floor.** A host is a supported Bindle provider when, and only when, it meets this minimum: (1) a valid manifest as above (supported `version`, exact issuer equality, every required endpoint on the issuer origin, `login_presentation` containing `redirect`, a `preferences_contract`); (2) the authorization code flow with PKCE S256 through `authorization_request_endpoint` and a top-level redirect, to exact registered redirect URIs, with `state` and `iss` on every callback; (3) single-use, short-lived codes and token responses that bind issuer, subject, client and audience ([wire profile](federation-implementation.md)). Every extension declaration, `popup`, revocation and DPoP declaration is optional, and clients MUST fully support providers that implement only the floor. A host whose manifest is present but below the floor is reported as an unsupported provider; it never triggers a fallback to another provider. Only a definitive 404/410 absence permits the fallback below, and errors never silently switch providers.

Successful discovery proceeds with OAuth authorization code plus PKCE S256, exact preregistered redirect URI, cryptographically random state, issuer binding and short-lived single-use codes. Public clients have no embedded secret. The app POSTs the complete handle as `identity` together with PKCE, registered client/redirect and fragment requests to `authorization_request_endpoint`, then redirects with only the returned `request_id`; [exact wire sequence](federation-implementation.md). The provider-stored request identifier references fragment grants; large grant descriptions MUST NOT be encoded unbounded in URLs. App registration requires verified control of its HTTPS origin and redirect URI. Registration is per provider unless the provider declares the client-id-metadata extension; open dynamic registration is not assumed by v0.

`redirect` MUST be supported by every provider and client. `popup` (in `login_presentation`) and FedCM (proposed, the fedcm extension) are optional; clients fall back to `popup` or `redirect` when a capability is absent or unsupported by the user agent, and use a FedCM config URL only from that issuer's manifest. Every transport ends in the same single-use authorization code bound to the authorization entry, PKCE challenge, state and issuer; exact FedCM, profile-defined delivery and DPoP exchange shapes are in [auth](auth.md#presentation-transports-and-key-binding). How a provider renders, frames or protects its pages is provider policy, not protocol.

A client MAY offer email login through a fallback provider it names only on an explicit 404/410 absence response, and only after showing the user that the entered address will be sent to that provider. Network, TLS, CORS, malformed-manifest, unsupported-version and HTTP 5xx failures MUST produce a retry/provider error, not silent fallback. Providers with manifests but unknown local users handle that condition themselves. A browser discovery CORS failure is not proof of absence; self-hosted providers MUST allow public manifest reads. Existing 3sln sessions never silently attach the email: email verification and an explicit account-link confirmation are required. Login/account association edge cases are specified in the security document.

## 3. Fragments and preference values

**AMD-C1 — proposed (approved provisionally 2026-10-20); replaced by extensions revision 3.1 (EXT3-25, owner-approved 2026-10-27).** AMD-C1 let fragment documents carry additional top-level members, which providers ignored. Extensions revision 3.1 (draft, unsigned, EXT3-25) replaces it with the exhaustive member table below: an unknown member anywhere in a fragment, including a top-level `slot` from extensions revision 2, makes the fragment unsupported ([extensions §10](extensions.md#10-what-revision-3-removes-and-compatibility)). Because this reverses a provisionally approved amendment, the owner was asked, and approved it on 2026-10-27 (DEVLOG, "Owner sign-offs (EXT3-25, setup exception)").

A fragment URL identifies an immutable schema version. Its members are exactly those in the member table below. Fragment documents MUST contain no entity values or secrets. Updates require a new URL; the provider pins the fetched canonical JSON SHA-256 digest at approval. A changed document at an existing URL is rejected pending review. (At a provider implementing the artefact-versions extension, a fragment URL is instead an append-only line: additive versions stay at the same URL and grants pin (URL, version, digest) under [artefacts §6 and §10](artefacts.md#6-additive-change), amendments AMD-R1 and AMD-R2, proposed. [Extensions §7](extensions.md#7-versioning-change-and-disappearance) applies this to fragments.) V0 schemas accept a bounded declarative subset, never arbitrary HTML, JavaScript, remote schema references or executable UI. Metadata is untrusted plain text.

```json
{
  "id": "https://drive.example/preferences/sync/v1",
  "title": "Sync storage",
  "description": "Choose where this application's files are stored.",
  "publisher": "https://drive.example",
  "fields": {
    "stores": {
      "title": "Storage locations",
      "type": "resource",
      "cardinality": {"min": 1, "max": 8},
      "contracts": ["https://3sln.me/artefacts/contracts/object-storage/v1"]
    },
    "theme": {"title": "Theme", "type": "enum", "values": ["system", "light", "dark"]}
  }
}
```

Atomic field types are string, boolean, integer, number, enum and HTTPS URL, with the explicit length/range members in the table below. Number precision is restricted to JSON-safe values; integers fit the safe integer range. Resource fields carry references, never adapter credentials. The optional scoping contract allows a shared `{resource,scope}` assignment; resource reads return independently attenuated tokens. See the [runtime scope rules](federation-implementation.md#authority-scoping-and-revocation). Resource constraints are an AND of required contracts; multiple alternative contract sets require a future explicit `anyOf`, not ambiguous interpretation. Cardinality applies equally to atomic/resource values; default is exactly one. Missing optional fields and an empty list are distinct. Fragments are configured per entity and immutable fragment version. Applications cannot write preference values in v0; only the user's authenticated provider UI can.

**Fragment members (extensions revision 3.2; draft, unimplemented; the fail-closed rule is owner-approved 2026-10-27, EXT3-25).** This table is exhaustive. A fragment containing a member it does not list, at any level (top level, field or `cardinality`), is **unsupported**: a required request fails with `unsupported_fragment`, and an optional one is reported `unsupported`. No provider applies part of a fragment's semantics. A fragment that uses a listed member wrongly (missing where required, on a field type it does not apply to, or out of bounds) is **invalid**. Adding a member is a revision of this specification, and a publisher who uses a new member publishes a new fragment URL; older providers then report it `unsupported` deterministically. A row whose "Defined by" column names an extension counts as listed only at a provider that implements that extension; no row does so today. Every member is part of the pinned fragment.

**Owner floor for resource fields (extensions revision 3.2; draft, unsigned except the initial-setup exception).** These rules apply to **every** resource field, not only to fields that carry `selection` (extensions EXT3-13). The detailed rules are in [extensions §3–§6](extensions.md#3-selection).

1. **Owner-only assignment.** Only the owner, through the provider's authenticated interface, sets, reorders, replaces or removes a resource-field value. No declaration, connection, discovery result, application or integration request, suggestion or announcement assigns a resource. A provider never assigns or switches one without an owner action, and that includes its own built-ins. Consumer failover under `selection` is not a switch, because it follows the owner's order.
2. **No oracle.** What an application, integration or external party observes MUST NOT depend on which resources fill, or which other consumers use, a field it is not approved for, beyond its own approved values and `requiresConsent`.
3. **Suggestions.** A provider MAY suggest candidates to the owner, drawn only from the candidates of [extensions §5.1](extensions.md#51-candidates) (built-ins, adapter resources, brokered offers and records, and contributed resources), matched on the contracts recorded for them. It MUST NOT preselect a candidate, MUST order candidates neutrally, and MUST NOT give its own built-ins any preference in order, prominence or default. Inside an authorization flow initiated by a client, no candidate is offered for a field that another consumer already uses or that admits provider consumers if any of these shares a registrable domain with that client: the candidate's origin, its supplying integration's origin, or the origin of its contributing producer client. Applications cannot suggest resource values ([incremental authorization §5.2](incremental-authorization.md#52-suggestions)). **Initial-setup exception (EXT3-26, owner-approved 2026-10-27):** during the provider's own initial account setup, never inside an application's flow, the provider MAY offer its built-in (for example hosted storage) as a choice labelled as provider-supplied, with its cost, beside an equally prominent option to decide later. It is never preselected, and only an explicit owner choice fills the field.
4. **Surfacing policy.** When and how often candidates are surfaced, within these rules and extensions §6, is provider policy. 3sln.me's policy will be a 3sln.me document, not part of Bindle.

**AMD-C2 — proposed (approved provisionally 2026-10-20).** Fragment requests MAY carry `digest`, encoded as `sha256-` followed by the unpadded base64url SHA-256 digest of canonical JSON. The provider MUST reject a request whose digest differs from its pinned or fetched document digest; it MUST NOT silently substitute a different document.

Apps request each fragment with `required`, a plain-text purpose, an explicit field set, and per-resource-field contract/method permissions. Fragment configuration does not imply application permission. A required grant is an application prerequisite, not forced user consent: declining cancels that application's connection with a clear explanation. Optional grants can be declined before configuration. Unconfigured required fragments show the request before the setup UI and receive final approval after values are chosen.

The final consent screen MUST show verified application origin (display name is not identity), each field/value shared, resource labels and providers, precise allowed methods including destructive/write operations, why the app requests them, fragment publisher metadata, and the consumers (applications and provider features) already approved for those fields. Shared fragment edits MUST show affected apps. Unverified metadata claims MUST NOT acquire a trusted badge. Users can review/revoke access later and cancel at every preapproval step. Only approved fields are returned to an app; schema metadata cannot expand the grant.

## 4. Grants and live authorization

A stored grant binds entity, client identity (for a provider feature, the issuer and the extension's spec URL, wherever a client identity is used, including journals and credentials; [extensions §4.2](extensions.md#42-provider-features)), fragment URL and pinned digest, field set, approved resource URLs and per-resource contract/method set. An access token binds issuer, subject/entity, audience/RPC endpoint, client and grant IDs with expiry. Tokens are opaque to SDK consumers. Access-token lifetime follows [auth](auth.md#token-lifetime-and-client-sessions): at most 15 minutes for Bearer and 60 minutes for DPoP-bound access tokens (user decision 2026-10-20, provisional); public-client refresh tokens, if provided, rotate with reuse detection, and a browser client may persist one only when it is DPoP-bound ([auth](auth.md#token-lifetime-and-client-sessions)). Component credentials a profile defines are never client or RPC credentials ([auth](auth.md#presentation-transports-and-key-binding)). Provider cookies are not application RPC credentials.

For every RPC, authority is the intersection of token grants, current nonrevoked grant records, current resource-field assignments, resource ownership, implemented contracts and requested method. Authorization is checked immediately before executing the operation. For issuer-hosted resources, removing an assignment or revoking a grant immediately blocks new operations, including operations using unexpired tokens. A process already streaming data may have disclosed bytes; revocation cannot recall them. Remote resource servers need token introspection or an equivalent revocation channel with a documented bound; v0 uses the issuer's adapter gateway unless the following declared exception applies. **AMD-C8 — proposed (approved provisionally 2026-10-20):** with the brokered-resources extension, provider-validated integration endpoints on the integration's own origin MAY receive consumer RPC and provider events under [integrations](integrations.md). Issuer-hosted RPC retains immediate revocation. Read-only brokered access MUST end by `access_ends_by` (at most 360 s after the severance commit), and earlier on acknowledged invalidation, even if the event is lost. Write-capable brokered contracts MUST require live introspection before execution, without cached authorization. A contract MAY opt out with `x-bindle-brokerable: false` or require method introspection ([contracts](contracts.md#contract-method-metadata)). No exception permits arbitrary endpoints or changes issuer-origin discovery, authorization or token endpoints.

Replacing or adding assigned resources never silently adds app access. Existing apps retain access only to the previously approved resources still assigned. The edit screen offers explicit reapproval per affected app; an app can later request a grant update. Removing resource assignments is immediate. Changing atomic values within already approved fields propagates to approved apps; the editor MUST explain this before saving. Adding fields, broadening methods, changing schema versions or restoring removed resources requires new approval. Assigning the same resource in another fragment does not bypass grant checks.

Provider and third-party integration credentials remain in server-side encrypted storage and MUST NOT be returned in preferences, RPC errors or logs. Adapter tokens authorize only the smallest available upstream scope; if an upstream provider offers broader scopes, consent discloses this limitation. Apps get approved resource capabilities, never upstream OAuth tokens.

## 5. RPC transport

POST the issuer RPC endpoint with `Authorization: Bearer …` and JSON. Transport is HTTPS. V0 consumer RPC is synchronous request/response; there are no consumer-supplied callback URLs, batch calls or fire-and-forget operations. **AMD-C8 — proposed (approved provisionally 2026-10-20):** provider events to validated integration endpoints are a separate channel governed by [integrations §6](integrations.md#6-events), not consumer RPC callbacks. Brokered RPC uses only the endpoint and audience in the approved preferences v2 projection; consumers MUST NOT send their issuer RPC token to an integration.

```json
{
  "version": "0",
  "tx": "2f17cceb-7cae-49cd-ae13-1aad1ceab264",
  "resource": "https://example.org/entities/e_123/resources/r_456",
  "contract": "https://3sln.me/artefacts/contracts/object-storage/v1",
  "method": "get",
  "args": {"key": "app/directory.json"}
}
```

Response: `{"version":"0","tx":"…","result":{…}}` or `{"version":"0","tx":"…","error":{"code":"conflict","message":"Object changed"}}`. Exactly one of result/error exists. Transactions are UUIDs generated by the app. Resource aliases are resolved before authorization and MUST be included in the canonical request fingerprint. Invalid envelopes return HTTP 400; missing/invalid bearer tokens 401; authorized, valid contract errors use HTTP 200 and the error envelope. Authorized requests denied by grant policy use 403 without revealing hidden resource existence. Servers enforce request/result byte limits and quotas and return 429 with Retry-After for rate limits.

The journal key is `(entity, client_id, tx)`; for a provider feature, `client_id` is its full client identity (issuer, extension spec URL) (§4). The fingerprint covers resolved resource, contract, method and canonical args. Repeating the same request returns the recorded outcome; reusing a tx for different content yields `tx_conflict`. Mutations require durable deduplication for at least 24 hours and advertised retention. Retried reads may use the same tx for the original snapshot or a new tx for fresh data. Clients MUST NOT retry a mutation outside the journal retention window as though guaranteed safe.

Exactly-once execution across external adapters cannot be guaranteed. Adapters MUST reserve the transaction durably before the upstream write and use upstream idempotency support where available. A crash/timeout with an unknowable outcome produces `indeterminate`, never an automatic second write; users/apps reconcile through a subsequent read. Validation, authorization and revocation checks precede cached response delivery: a revoked app does not recover a previously cached payload. V0 does not expose journal status through a separate anonymous endpoint.

**AMD-C4 — proposed (approved provisionally 2026-10-20).** `rate_limited`, `temporarily_unavailable`, `forbidden`, `not_found` and `unsupported_*` MUST be returned only when no effect occurred. An uncertain effect MUST be reported as `indeterminate`, never as one of these no-effect errors.

Common codes: `invalid_args`, `unsupported_contract`, `unsupported_method`, `not_found`, `forbidden`, `conflict`, `quota_exceeded`, `rate_limited`, `tx_conflict`, `indeterminate`, `temporarily_unavailable`. Error messages are safe for user display and omit upstream credentials and internal traces. Providers log audit metadata and transaction status but SHOULD NOT log argument/result payloads.

## 6. Compatibility and conformance

Contract method requirements and schemas are immutable at each URL. A resource lists the exact contracts it implements; matching by title, hostname or compatible-looking method names is forbidden. Compatible new methods use a new contract version unless a defined optional-method mechanism exists. Existing clients keep their approved version until migration/reconsent. Contracts may link human-readable documentation alongside JSON schemas with content negotiation, but identifiers and pinned semantic definitions remain stable.

Conformance tests MUST cover discovery/issuer confusion, manifest failures and fallback privacy; grant expansion/removal/revocation; schema substitution; alias authorization; cross-entity and cross-client calls; duplicate transactions and ambiguous upstream writes; malformed arguments; adapter credential nonexposure; pagination/concurrency; and accessible consent flows. Public resource descriptors reveal no private existence before authorization. Organization membership, delegation, public profile discovery, end-to-end encrypted storage, notifications and provider migration are deliberately outside v0.
