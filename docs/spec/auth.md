# Authentication and application authorization — v0 draft

> **Group:** Bindle core
>
> **Status:** proposed implementation baseline, provisional. The redirect flow is implemented locally by the 3sln.me reference host behind flags; popup completion, FedCM and the embedded-components envelope are proposed and not implemented. Nothing here is production-verified or a claim of external-provider conformance.
>
> **Covers:** identity discovery, application authorization (code + PKCE, transports, key binding), client sessions and their lifetime ceilings, and the envelope for extension-defined component credentials.
>
> **Does not cover:** how a provider runs its own sign-in (passkeys, passwords, email links, browser sessions); for 3sln.me see [sign-in and sessions](../3sln/accounts/sign-in-and-sessions.md). A signed-in browser approving *another browser* so that it gets a provider session (session handoff): that is provider policy, not an app grant; for 3sln.me see [approve a sign-in](../3sln/accounts/approve-a-sign-in.md). Local clients (`localhost` web apps, per-installation CLIs) have no specification yet; the design is in the [local clients spike](../architecture/local-clients-spike.md).

## Identity and discovery

A handle is a discovery hint, not the durable account key. The durable subject is a provider-issued HTTPS identity URL; clients key identities by issuer plus subject and MUST NOT merge them by email, display name, or handle. Email ownership and domain ownership can change.

Clients resolve only a complete handle; how a client collects or completes it (for example a default host for unqualified input) is presentation and outside this specification (3sln.me reference-host choices are in [3sln.me security policy](../3sln/release-gates.md#reference-host-presentation-and-framing-3slnme-policy)). Preserve local-part spelling; trim surrounding whitespace, normalize domain through IDNA, and reject control characters, URL credentials, paths, fragments, IP literals, and unsupported ports. v0 handles contain one separator and a nonempty local part and DNS host. Email fallback supports ordinary ASCII mailbox forms; unsupported email syntax receives a clear error, not guessed normalization. Never strip dots or plus-tags or lowercase local parts.

Discover `https://<host>/.well-known/bindle/manifest.json`. `https://<user>@<host>/...` is forbidden: the user segment is URL userinfo and is not account routing. The manifest describes a provider, not whether a particular person exists. Pass the complete account hint to the authorization endpoint as `identity` in the bounded authorization-request POST; its interpretation belongs to that provider. Manifest discovery MUST use HTTPS, bounded responses, schema validation, and an exact issuer origin match. v0 requires authorization, token, and RPC endpoints on that origin, disallows redirects during manifest fetch, and requires CORS for browser discovery. Advanced delegated hosting needs a future explicit trust profile.

Discovery outcomes:

| Outcome | Behavior |
| --- | --- |
| Valid supported manifest | Continue to named provider; provider handles unknown local account. |
| HTTP 404 or 410 from host | A client MAY offer clearly labeled email login through a fallback provider it names; user confirms sending mail. |
| DNS, TLS, timeout, CORS, 401, 403, 429, 5xx | Explain unavailable discovery and allow retry. Do not interpret as no provider. |
| Malformed JSON, invalid issuer, unsupported version, unsafe endpoint, or below the [conformance floor](protocol.md#2-discovery-and-login) | Fail closed with actionable unsupported-provider message; never fall back to another provider. |
| User intentionally chooses email login despite unavailable provider | Separate explicit action at the named fallback provider; explain that it creates/uses an identity there, distinct from any hosted identity. |

Whether a manifest exists is public provider metadata; the host-level discovery endpoint MUST NOT enumerate individual accounts. The current targeted authorization-request profile resolves an explicitly supplied handle and exposes availability and its public UUID locator; this is a documented product/privacy tradeoff with restrictive admission limits, not an enumeration-proof claim. A host manifest cannot prove that a submitted mailbox belongs to the user.

## Application authorization

Use OAuth authorization code flow with mandatory S256 PKCE. The redirect flow with exact registered callbacks and issuer binding is the conformance floor every provider meets ([protocol §2](protocol.md#2-discovery-and-login)); everything else in this section is optional and declared in the manifest. Public browser SDKs have no client secret. Providers register clients and exact HTTPS redirect URIs (or, when declaring `client-id-metadata.v1`, resolve an HTTPS `client_id` to its metadata document under their own review policy); localhost HTTP is allowed only in an explicit development configuration. A client ID alone is not evidence that an app is trusted. Display registered origin, app name, requested fragment versions, requested methods, purpose, required/optional status, and current recipients. Treat developer purpose text as unverified text.

The SDK generates cryptographically random `state`, a PKCE verifier, and a transaction record bound to issuer, client, redirect URI, requested fragments, and expiry. Use a top-level redirect by default. After callback, validate state and issuer, exchange the single-use short-lived code, and erase the transaction. Validate issuer identity at token exchange; never send a code or verifier to an endpoint obtained from callback input. A replayed authorization code revokes the client session issued by its first redemption (RFC 9700 §4.5). The token response binds the subject, client, audience, grants, expiry, and granted fragment revisions. Authentication does not implicitly approve data access. If identity claims use an ID token, implement OIDC validation including nonce, audience, signature, expiry and issuer; do not invent an unsigned equivalent.

### Presentation, transports and key binding

This specification defines no user interface. It defines which transports a provider supports and the exact exchange shapes; how a provider renders, frames or protects its own pages is provider policy (3sln.me policy: [3sln.me security policy](../3sln/release-gates.md#reference-host-presentation-and-framing-3slnme-policy)).

- **Capabilities.** The manifest `login_presentation` array lists supported transports. `redirect` (top-level navigation to the authorization endpoint and back to the exact registered redirect URI) MUST be supported by every provider and client. `popup` means the provider's authorization pages work in an auxiliary top-level window and complete exactly as redirect does (below). FedCM (proposed) is declared by the `fedcm.v1` feature ([protocol §2](protocol.md#2-discovery-and-login)), whose `config_url` is an HTTPS URL on the issuer origin; it means the provider is a [FedCM](https://w3c-fedid.github.io/FedCM/) identity provider. Clients MUST fall back to `popup` or `redirect` when a capability is absent or the user agent lacks it, and MUST only use a FedCM config URL obtained from that issuer's manifest.
- **FedCM exchange (proposed).** The client first creates the authorization entry with `presentation:"fedcm"`, then calls FedCM with `params` exactly `{"v":1,"entry":"<entry id>"}` (plus members a declared profile defines) and the registered `clientId`. The provider's ID assertion endpoint MUST require the browser-set `Origin` to be a registered origin of `client_id` (never a component origin: components do not delegate to FedCM, below), MUST bind the entry to the selected account at most once, and returns either `token`, a JSON text `{"v":1,"code":"…","state":"…","iss":"…"}` (a declared profile MAY add members delivered only to that profile's components), or `continue_on` for further provider interaction ending in the same token. The client validates `code`, `state` and `iss` exactly as callback parameters and performs the ordinary PKCE exchange. A FedCM token MUST NOT be an access token. Non-approval is `{"error":{"code":"access_denied"}}`.
- **Extension-defined delivery and component credentials (proposed).** The Bindle-owned embedded-components extension ([extensions §2.7](extensions.md#27-extensions-cannot-change-core), provisional; its content is currently the [components profile](../profiles/components-v1.md), pending republication) MAY define provider code that runs outside the issuer origin (a *component*) and additional ways to deliver an authorization code. This specification fixes only the envelope that extension stays within. The **component origin** is the origin of that extension's `embed_origin` option, declared in the issuer's own manifest, one per issuer. It need not be on the issuer origin (it may be a subdomain or an associated site the provider operates), and it is authoritative because the issuer's own manifest declares it. Only that origin, and only together with a fresh proof of a key that the profile defines and the authorization entry names, may create authorization entries for a registered client; the provider refuses such entries without the proof and refuses component-only entry members from any other origin. The envelope does not cover FedCM: components never delegate to FedCM, so the component origin creates authorization entries only and never presents a FedCM ID assertion request (extensions rev 3.3 §2.7, CR-X3-33, provisional). Codes may pass through the component origin, but the client always receives an ordinary authorization code with `state` and `iss`, bound at exchange to its own PKCE challenge, `state`, issuer and registered `redirect_uri`, delivered only to documents whose origin is the origin of that `redirect_uri`, and validated exactly as callback parameters. Credentials that authenticate a component MUST NOT reach the client in any redirect, token response, callback or message, and MUST NOT be accepted at the token, revocation or RPC endpoints. These conditions exist because a component runs framed inside other sites' pages under browser storage partitioning, not because the provider's ownership of the component origin is in doubt. Nothing here changes consent, grants or token semantics. Everything else (component behaviour, framing, messages, how component credentials are attested and bound) belongs to the extension.

Popup completion (proposed, decision D7 of [embeddable elements](../architecture/embeddable-elements.md); no provider implements popup presentation yet): the provider ends the flow exactly as in redirect mode, with a top-level redirect to the exact registered redirect URI, and never sends messages to the client window. The client MAY relay the returned callback parameters (`code` or `error`, `state`, `iss`) from its own callback document to the document that started the transaction, only within the client origin (for example a same-origin `BroadcastChannel` whose name is derived from the state). Relaying is client-internal: the receiving document still applies the full callback validation, the code stays bound to the PKCE verifier held only by the initiating document and to the single-use transaction, and tokens never traverse cross-origin or wildcard messaging.

### Token lifetime and client sessions

Access tokens target only the provider RPC audience and stay in memory. **Lifetime (user decision 2026-10-20, provisional; supersedes the earlier five-minute limit and the 30-day absolute / 7-day idle client-session cap):** a Bearer access token lives at most 15 minutes and a DPoP-bound access token at most 60 minutes; a provider MAY configure shorter lifetimes. A public client's refresh token MUST rotate on every use with reuse detection, and every renewal MUST check the live grants, client connection and account status, plus the approval lineage where one exists ([device authorization §7](extensions/device-authorization.md#7-credential-lifetime)). Issuer-hosted RPC MUST perform the same live grant, connection, account and lineage checks on every call, so longer access tokens never delay revocation or suspension. A client session needs no absolute lifetime: it ends by revocation, reuse detection, a failed live check or an idle limit. A provider chooses its idle limit (3sln.me's values: [sign-in and sessions](../3sln/accounts/sign-in-and-sessions.md#app-session-lifetimes-on-3slnme)). `refresh_expires_in` is the lifetime of the issued refresh token: without an absolute limit it equals `refresh_idle_expires_in`, and each rotation renews it. Clients MUST NOT treat it as a session deadline that can only move earlier. The user's involvement is one fresh passkey or password confirmation at approval. A browser client MAY persist a refresh token across reloads (proposed) **only** if it is sender-constrained with [DPoP, RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html): the authorization entry carries `dpopJkt`, the code exchange and every refresh carry a DPoP proof for that key (which binds the refresh token to it, per RFC 9449 §5), and the provider advertises `dpop_signing_alg_values_supported` and `refresh_idle_expires_in` alongside `refresh_expires_in`. Unconstrained refresh tokens stay in memory. `token_type` describes only the access token: a provider MAY issue Bearer access tokens (at most 15 minutes) alongside a DPoP-bound refresh token; clients MUST accept either `Bearer` or `DPoP` and send DPoP proofs with resource requests only when `token_type` is `DPoP`. Rationale: RFC 9700 §4.14 requires sender-constraining or rotation for public-client refresh tokens; persistence requires both, so a token read from storage is unusable without the key. It does not stop script running in the client from starting a new authorization with a key it can export; providers SHOULD therefore not issue persistent refresh tokens or component credentials for authorizations that completed without a user interaction (for example a browser-auto-selected FedCM assertion), SHOULD require DPoP server nonces, and SHOULD bound client sessions per client and account. One successful code exchange creates one **client session** that owns its refresh family and any paired component credential; revoking the client's connection, revoking the client session (including RFC 7009 revocation of its refresh token), or detected refresh-token reuse revokes all of them immediately. How a provider keeps its own login sessions is provider policy. Confidential backends remain the recommendation for high-value background access. Client sign-out and provider session end are distinct (proposed, decision D8; provider endpoints not yet implemented). Client sign-out clears the client's memory state and pending transaction, and MAY revoke that client's own tokens at a provider-advertised revocation endpoint (RFC 7009 style); it does not end the provider session. Ending a provider session is a separate request through the provider's authorization entry with an end-session intent, which the provider confirms on its own page and which returns only `state`, `iss` and `result=completed|canceled` to the registered redirect URI; a provider without a session for that account still returns `completed`. Providers MUST NOT end sessions on GET, image or frame loads, or cross-origin messages. Grant revocation is a separate explicit action. Revocation MUST block issuer-hosted RPC immediately, regardless of unexpired tokens. **AMD-C8 — proposed (approved provisionally 2026-10-20):** direct integration RPC is permitted only under `brokered-resources.v1`, with a separately minted integration-audience token from preferences v2. A conforming integration MUST reject invalidated authority on acknowledgment and no later than `access_ends_by` (at most 360 s after commit) for read-only brokered access even if invalidation is lost. Write-capable brokered contracts MUST require live introspection without cached authorization before execution. Contract opt-out and stricter method introspection rules apply ([contracts](contracts.md#contract-method-metadata), [integrations §7](extensions/integrations.md#7-severance)). This exception does not relax immediate provider-side refresh revocation or minting refusal.

## Sign-off checkpoints

- [ ] **A1 — Federation identity:** issuer plus stable subject; host manifest; fail-closed discovery; email fallback is a separate identity.
- [ ] **A2 — Auth profile:** code + PKCE over redirect (universal), popup or FedCM (advertised); registered clients and exact redirects; no UI requirements in the spec.
- [ ] **A5 — Session scope:** access tokens ≤ 15 min Bearer / ≤ 60 min DPoP-bound with live checks on every RPC; rotating refresh with live checks; no absolute client-session lifetime (provisional, 2026-10-20); browser persistence only when DPoP-bound; component credentials never authorize RPC; one revocable client session.

A3 (account linking) and A4 (email recovery) moved with the hosted-account rules to [sign-in and sessions](../3sln/accounts/sign-in-and-sessions.md#sign-off-checkpoints).
