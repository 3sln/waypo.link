## One URL, three explicit operations

An entity shares a signed contact endpoint, as a link or QR code:

`https://3sln.example/users/alice/contact/ENDPOINT_ID?sig=ENDPOINT_JWS`

Examples use the reserved `.example` domain until publication authority is agreed. The ordinary URL path identifies the endpoint; URL userinfo such as `https://alice@host` is not an account route. The signed query is the capability. Possession authorizes message submission within the live invitation's scope and quotas, not sender identity, inbox reading, account login or owner actions.

| Request | Representation or operation |
| --- | --- |
| `GET` with default/browser HTML acceptance | Human composer UI; verifies the capability but never sends a message or consumes delivery quota. |
| `GET` with `Accept: application/vnd.bindle.contact-token+jwt` | Returns a distinct compact inbox bearer JWT as the response body, with that Content-Type and `Cache-Control: no-store`. Minting never delivers a message or adds a per-token database record. |
| `POST` to the same signed URL, `multipart/form-data` | Identity-authored delivery: exact `envelope` and `message` parts under [contact delivery](contact-delivery.md), with optional `Idempotency-Key` header. The receiver enforces endpoint scope and live quotas atomically. |

**Cutover implemented locally (user decision 2026-10-14).** Link delivery on both URL forms requires identity-authored contact-delivery v1. Anonymous multipart and inbox-bearer submission at `/api/messages` are refused with `author_required` (403). Negotiate `Accept: application/vnd.bindle.contact-token+jwt; profile="contact-delivery-v1"` for the distinct contact-only bearer used at `POST /bindle/rpc`. Legacy inbox bearer minting is retained only for compatible conversation invitations; it grants no anonymous message submission. The front-end SDK app-connection path ([app messages](../../../../docs/3sln/services/app-messages.md)) remains separate.

Unsupported methods return 405; unsupported negotiated representations return 406. The adapter must apply normal Accept specificity/quality semantics, rather than treating a header substring as consent to any representation. HEAD, link previews, prefetches and scanners never deliver. No redirect to third-party hosts is allowed in this flow. A contact-delivery-v1 bearer is presented to the issuer's contact-only `POST /bindle/rpc` dispatcher in `Authorization: Bearer TOKEN`; legacy inbox bearers cannot submit messages. It is not itself a replacement endpoint or a signing key.

Machine requests may use capability-based CORS (`Access-Control-Allow-Origin: *`) without credentials, owner cookies or session-dependent results. Preflight grants only the documented methods/headers and does not mint or deliver. The capability is the authority; CORS is not an authorization boundary. Implementations serving personalized owner state must not mix that state into this public capability response. SDKs fetch only the user-supplied verified endpoint, omit credentials and refuse cross-origin redirects.

## Signature profiles and key custody

Both profiles use compact [JWS](https://www.rfc-editor.org/rfc/rfc7515), ES256 (P-256/SHA-256) or EdDSA/Ed25519. Edwards-key JOSE encoding follows [RFC 8037](https://www.rfc-editor.org/rfc/rfc8037). Only locally registered account public keys are accepted; `none`, HMAC, embedded public-key substitution and remote key discovery are unavailable.

The endpoint protected header is exactly `{alg,kid,typ:"bindle-contact-endpoint+jwt"}`. Its claims are `{iss,sub,aud,jti,iat,exp,collections,mimeTypes,maxMessages,maxBytes,maxMessageBytes,requiredTags,optionalTags}`. `aud` is the exact canonical endpoint URL without its query, `jti` is the parent grant/endpoint ID, and `sub` is a stable account ID. The selected handle is part of the signed URL audience; moving or renaming that route requires an explicit compatibility policy or new endpoint, not silently rewriting its signature. The server stores the exact immutable header and claims on the parent grant before accepting the endpoint. A cryptographically valid signature alone never authorizes arbitrary newly invented claims.

The inbox protected header is exactly `{alg,kid,typ:"bindle-inbox+jwt"}`. Its claims inherit the exact parent collection/MIME/quota and (until the intake-configuration change above ships) required/optional tag scope, issuer and stable subject, with `aud = ISSUER/api/messages`, random `jti`, `parent = ENDPOINT_ID`, `endpoint = CANONICAL_ENDPOINT_URL`, and current `iat`/`exp`. Lifetime is at most 300 seconds and never extends parent expiry. The bearer ID is not persisted. Validation compares all inherited claims to the live parent, validates mint-time bounds and signature, and rejects unknown or expanded claims. An endpoint JWS cannot be used as an inbox token; the types and audiences are distinct.

Core signing receives an injected `signer({owner,kid,alg})` returning a private CryptoKey and stores public JWKs only. Hosted v0 can use a server-custodied per-account key encrypted at rest. UI must describe it accurately as an account signing key held by the service, without claiming user-exclusive custody or end-to-end encryption. Passkeys authenticate the owner; they are not automatically general-purpose JWS signing keys. Device-only signing and key enrollment/recovery require a separate reviewed protocol. Retiring a key invalidates its endpoints and existing bearers immediately.

## Live grants, limits and metadata trust

`ContactEndpointService({tokens,signer})` builds on the existing grant/key registry. `create(owner,{handle,...grantOptions})` returns `{grant,url,endpoint}`. `inspect(url)` verifies without writes; `mint(url)` returns `{token,tokenType:"Bearer",expiresAt,contentType}`. Its `verify(token)` and `live(tx,verified)` are the MessagingService token interface; `live` returns the parent record so every minted bearer shares quotas and idempotency receipts. The internal inspection record is not a public HTTP response: do not expose recipient quarantine status, counters, rules or private account metadata.

Acceptance rechecks key/parent activity and expiry, collection ownership, exact MIME allowlist, decoded size, remaining parent quota and account storage quota in the message transaction. Revocation blocks future minting, sends and idempotent replays from already minted bearers. Quarantine remains a live parent flag: accepted messages become quarantined and do not notify, including when sent with a previously minted bearer. Quarantine is silent to link holders: the profile, intake metadata, preview, redemption and conversation-invitation answers of a quarantined parent are the same as for the active parent, and delivery still answers 202 (provisional, DEVLOG 2026-10-23). Known residual inference channels: a redemption made while quarantined is answered but not recorded, so the redeemer's later contact-info lookups show no owner-disclosed profile until it redeems again after release, and a second holder's redemption is answered 2xx where a recorded binding would answer 409. A conversation invitation through a quarantined parent creates a hidden, quarantined room that needs the owner's acceptance, and once ten such rooms are pending, further quarantined invitations are refused with `conversation_room_quota` (429) while an active parent's would still be admitted. Disabling a target collection revokes associated parents. Scope changes mint a new parent endpoint, never enlarge old shared copies.

**Superseded for `bindle_meta` links (user decision 2026-10-14; intake implemented locally, see links, in git history: `git show bbbbdad:docs/spec/superseded/links.md`):** signed `requiredTags` and `optionalTags` leave the link/token claims. Auto-associated tags and the sender-selectable allowlist become mutable, revisioned, server-side per-link intake configuration that the owner edits without reissuing the link; legacy signed values seed the intake configuration initially, and later changes apply to existing links and minted bearers. The following still describes legacy `?sig=` endpoint grants. They include signed `requiredTags` and `optionalTags`: disjoint, unique plain strings with at most 32 combined entries and 64 characters per entry. Required tags are added automatically on delivery. A sender may select only permitted optional tags; repeating a required tag is harmless and deduplicated. Selecting any other tag rejects delivery before storage or receipt quota consumption. Both tag lists are inherited exactly by a minted bearer. A grant with only one of the two lists is invalid. Historical grants lacking both retain their old semantics: sender tags remain annotations and do not become endorsed delivery tags.

Sender-supplied `subject` (up to 200 characters, no control characters) and `tags` are also recorded separately as `senderMetadata` and rendered as text. For new grants, validated required/selected optional tags initialize owner tags and can match `tagsAll` rules; arbitrary raw annotations cannot. Owner rules may subsequently change organizational tags or classification. Original authorized delivery tags remain the rule input, avoiding cascades. Tags grant no reading or automation permission and cannot bypass quarantine. Idempotency includes sender metadata, MIME, legacy target and bytes.

Messages and conversations form one logical incoming stream; configurable Views project that stream using metadata filters. Contact tag policy organizes incoming items without choosing a priority inbox. Existing `collections` claims remain immutable legacy authorization partitions during migration. A View is never a replacement for those claims.

Current parent caps are 32 selected collections, 32 exact lowercase MIME types, 366 days, 100,000 messages and 1 GiB cumulative bytes, with a 10 MiB per-message ceiling and 1,000 active, unexpired parent grants per account. Revoked and expired parents do not count; the reference host reclaims them, with their name and stored-URL rows, after they have been dead for the receipt retention window and every receipt and replay fence they own has passed `retainUntil`, and tombstones the parent ID so it can never verify again (provisional, DEVLOG 2026-10-23). The tombstone records the parent's signed `exp` and is collected once that `exp` (plus clock skew) has passed, since nothing naming the ID can verify after it; a tombstone without a recorded `exp` is kept for the 366-day maximum parent lifetime after reclamation (provisional, DEVLOG 2026-10-23, round 3 L5). Defaults are 100 messages, 10 MiB cumulative and 1 MiB per message. Minting creates no child rows, preventing unbounded stored-token growth; it still needs request-rate and signature-computation limits. Transport body limits apply before multipart buffering. Invalid endpoint/signature/expiry/unknown-grant responses are uniform and disclose no collection existence; authorized scope errors must also avoid leaking unrelated resources.

## URL secrecy and browser handling

The new query signature necessarily reaches the HTTP server and may enter infrastructure logs. Configure query redaction or omit query strings from access logs, trace spans, analytics, crash reports and CDN debugging. Every endpoint representation needs `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, with no third-party scripts, images or analytics. Never include the signed URL in notification payloads or service-worker caches. QR scans, browser history, clipboard managers, extensions, screenshots and recipients can disclose it; the UI must offer revocation and regeneration.

The human composer captures the full signed endpoint URL in memory before scrubbing the query using `history.replaceState`. Its intentional POST uses that remembered URL. Scrubbing must not break submission or transform the capability into owner authentication. Reload after scrubbing may require reopening the original shared link. A browser GET or machine token request does not consume a message quota or send anything. The earlier fragment helper and `contact+jwt` tests remain compatibility-only internal code; new public links and protocol documentation use signed endpoints.

Required release checks include actual HTTP representation negotiation, default/no-Accept HTML, scanner-safe GET/HEAD, multipart duplicate/size/type handling, CORS with credentials omitted, query/header log redaction, parent revocation/quarantine races, distinct token-type rejection, no minted-token state growth, browser history and service-worker behavior, and independent security review. Unit tests do not establish real network or operational gates.


## Contact profile, sharing and saved contacts

Provisional, unsigned (moved here from the superseded beaming specification on 2026-10-26, in git history: `git show b7c04cc:docs/spec/superseded/beaming.md`; Reviewer ___ Date ___ Outcome ___). Whether saved contacts belong in the core is a pending user decision.

An account may keep an optional profile with the self-asserted presentation fields `displayName`, `bio` and `avatar`, and a global `discloseToContacts` switch that defaults to off. Each contact-link grant has a `profileFields` allowlist, initially empty, drawn from those fields. Disclosure requires both the global switch and the exact live grant's allowlist; a different grant for the same person must not expand the fields returned for this link. A name or avatar is never called verified merely because a session is authenticated; the account identity is authenticated and labelled separately, even when no profile is shown. The local UI presents an avatar URL as an explicit external link and does not fetch the remote image on contact review.

The signed endpoint supports a public, capability-authorized contact-profile representation under `application/vnd.bindle.contact-profile+json`, a project-private proposed media type with no IANA registration claimed. Holding the exact live signed link is sufficient to request its owner-selected fields; account login and saving the contact are not prerequisites. Disclosure consent must therefore say **anyone holding this link can read its selected fields**. Profile reads verify the signature and live parent, handle a quarantined parent silently as described under live grants above, respect media-type quality and explicit exclusions, use no-store/no-referrer, return no device inventory or internal grant state, and never mint a token or establish a relationship as a side effect.

Redemption is a deliberate authenticated POST that binds the redeemer to the live endpoint grant, so directory reads can apply that particular grant's allowlist. Saving an ordinary signed contact link grants no other authority. GET, link previews and QR scans never silently save a contact or grant authority. The saved-contacts directory keeps bounded entries: an encrypted copy of the signed link, the account identity and only the fields the owner chose to disclose. The user can remove an entry; only the link owner can revoke the grant.

Reference routes (authenticated owner session unless noted): `GET` and `PUT /api/profile` (`GET` also returns an opaque content `revision`; a `PUT` may name it as `expectedRevision` and is then refused with `409 profile_stale` when the stored profile no longer has that content, so a client cannot overwrite a profile it has not loaded; provisional, 2026-10-27); `PUT /api/contacts/{id}/sharing` with body `{profileFields}` (formerly `/api/contacts/{id}/beam`); `POST /api/contacts/redeem`; `GET /api/contacts/directory`; `DELETE /api/contacts/directory/{peer}`; `GET /api/contacts/profile/{peer}`. Account storage uses `profile`, `saved-contact/<peer>`, `contact-sharing/<grantId>`, `contact-redeemed/<grantId>` and the derived index `contact-redeemed-peer/<peer>/<grantId>`. For one release (`beam-retired-v1`), so that a rollback to the pre-removal code stays correct, every write also keeps the former `beam/` twin with the same `updatedAt` stamp, every delete removes both, and the legacy row stays authoritative: reads take it unless both rows are stamped and the neutral one is newer, and a neutral row without a legacy twin reads as deleted. The idempotent `beam-retired-v1` account step copies legacy rows forward without deleting them; a later `beam-retired-v2` step deletes them after a release. The profile, saved contacts, sharing grants and redemption bindings are account-export families (exported from the authoritative legacy row during v1); the peer index is excluded as derived. A sharing change naming both `profileFields` and `discloseProfile` is refused.


## Typed delivery design

The [contact-delivery candidate](contact-delivery.md) specifies a common envelope for signed-URL POST and narrowly authorized contact-bearer RPC, with explicit one-off versus conversation-initiation semantics. Its authored one-off path is implemented locally; it does not expand legacy inbox-token authority or establish conversation-v2 conformance. Senders must negotiate the explicit contact-delivery-v1 profile.
