# Notification protocol and engine extension (proposed)

Status: protocol design with a locally implemented reference notification and configured protected-action profile. Deployment limits remain operator policy, not protocol guarantees. Production remains disabled. This document records the notification workstream design; changes require coordinator agreement on interfaces before parallel implementation. No cloud operations are part of this work.

## Current implementation and boundaries

`packages/services/notifications.mjs` is a portable ngin engine with transactional KV, authorization, clock, scheduling and delivery ports. Each issuer/user/client namespace contains an array of at most 32 queued messages, eight routes, 16 rules and 16 enqueue receipts. Current messages are plain title/body/tags. Inbox reads scan that bounded array; dismiss deletes; there is no seen/pin/search/action protocol. Owner HTTP routes presently configure routes/rules; service routes read/dismiss app-private inboxes. Push device verification proves receipt of a challenge, not human viewing. Current push delivery contains title/body and must change before claiming privacy-preserving defaults. Node SQLite currently exposes one JSON KV table, so indexed search requires a new transactional query port and migrations, not a larger array.

Installed dependencies include `jose`, `@simplewebauthn/server`, Better Auth OAuth/passkeys, and ngin. Reuse these implementations. A server-side HTML parser is not currently a direct dependency. Do not use regex stripping or claim a browser-only renderer can sanitize authoritative server input.

The protocol defines interoperable security/content meanings. Reference deployment policy defines quotas, defaults and retention choices. Hosted Waypo.link composition supplies branding/commercial policy; OSS Waypo remains self-hostable. Hosted issuer is `https://waypo.link/api/auth`; web UI stays on the main origin. Mail domain separation (login/account/notify) creates no extra web origin. Sender identity is provider-owned chrome outside app content.

## Human and node flows

1. An app authenticates through the existing OAuth flow and receives consented notification authority. The server derives its client from verified authority, never from enqueue JSON. The SDK discovers support and validates input early; authoritative validation is repeated server-side.
2. The app sends an idempotent message. The engine validates content, verified URL authority, bounded action credentials and retention hints, persists normalized content/index rows atomically and routes delivery under current consent. Sender identity is resolved from the authenticated client registry.
3. A device receives a generic push by default. Opening it focuses/opens the provider inbox message; when a verified target exists an explicit ordinary click can open that target. No target means full message view in Waypo. Push reception, background synchronization and previews do not mark seen.
4. A visible foreground message view acknowledges first-seen through an owner-authenticated command. The UI requires actual visible content and a meaningful dwell or explicit “mark seen”; the server records only the earliest accepted time. Clients cannot report arbitrary historical timestamps. Pins and deletes are explicit owner commands.
5. A link action opens its validated app URL with opener isolation. A POST action displays its exact app, purpose and submitted fields, obtains fresh action-bound UV when required, and calls the endpoint from foreground UI. Service workers never execute side effects on mere push delivery.
6. The app validates its intended recipient, action digest, expiry, approval proof where required, stable idempotency key and any optional app-issued action token before applying a side effect. Retries return the original result. The provider displays a bounded plain-text localized result, or offers a newly validated app-owned URL.

## Proposed v2 message wire shape

Unknown security-sensitive fields fail closed. Version negotiation keeps old clients from bypassing policy. Preserve the existing plaintext v1 path only under the same privacy defaults and URL restrictions; v1 cannot request actions.

```json
{
  "version": 2,
  "requestId": "request_42",
  "title": "Order ready",
  "content": {"format": "html", "value": "<p>Your order is ready.</p>"},
  "tags": ["orders"],
  "deadlineAt": 1793750000000,
  "deadlineWarningMs": 86400000,
  "target": "https://shop.example/orders/42",
  "push": {"mode": "generic"},
  "retention": {"suggestSeenDays": 30},
  "actions": [{
    "id": "confirm", "label": "Confirm collection", "kind": "post",
    "url": "https://shop.example/api/collect",
    "fields": [["order", "42"]],
    "authorization": {"token": "opaque-app-issued-capability", "expiresAt": 1793750000000},
    "nonce": "app-generated-random-one-use-value",
    "verification": "required"
  }]
}
```

`target` is optional. Link actions use `{id,label,kind:"link",url}` and no token. POST fields are ordered string pairs, permitting repeated names without prototype confusion; no files, arbitrary headers or executable templates. JSON body carries these fields, any optional app-issued action token, nonce, approval proof if required, and action/message IDs. App endpoints adapt that envelope to their form handler; the provider does not submit browser forms or guess CSRF conventions. Plain content uses `format:"text"`. Full HTML input is limited to 4096 UTF-8 bytes before parsing; sanitization cannot be used to evade admission limits.

Provisional engineering caps: title 120 characters; four actions; action label 48 characters; URL 2048 UTF-8 bytes; 16 field pairs, 64-byte names and 1024-byte values, 4096 aggregate field bytes; token 2048 bytes; total enqueue 16 KiB. In the optional app-token profile, tokens expire no later than seven days after enqueue; apps requiring longer availability must expose a link or refresh workflow. Server error codes distinguish invalid shape, unverified destination, delegation expired, action expired and capacity exceeded; SDK errors name the failing field and remediation. These caps are proposals, not approved plan entitlements.

## URL authority

Use a single canonical URL validator for targets, rich hyperlinks, link/POST actions and returned open URLs. Require canonical absolute HTTPS, no credentials or fragments for POST, no control characters, encoded host ambiguity, IP literals, local/private hosts or nonstandard ports in the public profile. Reject backslash/protocol-relative tricks rather than attempting permissive repairs. Compare parsed exact origins (scheme/host/port); suffix matching is forbidden. Plain HTTPS rich links need the same ownership policy to avoid an app embedding foreign action affordances.

Same-origin authority comes only from a verified client identity URL, such as a validated HTTPS CIMD client identifier, or an operator-verified first-party client origin. A client-declared homepage, redirect URI, logo or arbitrary metadata origin does not independently prove ownership. Arbitrary opaque client IDs require explicit verified origin enrollment.

Additional origins publish a small destination-hosted document at a fixed well-known path, proposed `/.well-known/waypo-notification-delegation`. Each grant binds issuer, exact OAuth client identifier, destination origin, permitted purpose (`navigate`/`post`), exact path or explicit segment-bounded path prefix, expiry and revision. This is a Waypo extension, not an established standard. Destination publication proves destination consent; it does not assert common legal ownership. Restrict grants to a short revalidation lifetime, provisionally 24 hours. No origin wildcards. Fetch only through the existing safe public egress approach: public resolved addresses, HTTPS verification, response/size/time caps, no redirects, no private fallback and DNS-rebinding protection on the actual connection. Cache by issuer/client/destination/purpose and record proof revision. Check at enqueue and action execution, including response navigation. SDK checks aid diagnosis and never replace authoritative verification.

Direct browser POST avoids provider-side action SSRF. Browser CORS is not authorization or proof of destination ownership. Browser private-network protections vary; approved public endpoint enforcement and DNS changes remain a documented limitation unless a controlled public egress gateway is added. Do not silently add such a gateway: it changes trust, availability, token exposure and egress economics.

## POST transport, results and idempotency

Use `fetch` with `mode:"cors"`, `credentials:"omit"`, `redirect:"error"`, `referrerPolicy:"no-referrer"`, bounded timeout, JSON content type, `Accept: application/json`, chosen locale in `Accept-Language`, and stable `Idempotency-Key`. No provider access/session token, app cookies, HTTP auth or reusable OIDC assertion is forwarded. Endpoint CORS permits the provider origin and required headers. Redirects are errors, including same-origin redirects. An HTTP error or invalid/oversized response never triggers navigation; a network timeout is an unknown outcome, not proof the side effect failed. Retry uses the same key/digest and, if applicable, the same app token.

Return UTF-8 JSON (maximum 4096 bytes), for example:

```json
{"version":1,"kind":"message","status":"success","message":"Collection confirmed."}
```

`status` is `success|error|info|warning`; `message` is bounded plain text (proposed 512 characters). Or return `{version:1,kind:"open",url:"https://shop.example/orders/42"}`. Validate returned URL ownership again, then render an explicit “Open app” control in a new tab. Browser popup restrictions mean a late async response cannot guarantee automatic new-tab opening; do not preopen an untrusted blank tab or claim this is reliable. Never interpret response HTML, Unicode custom headers or arbitrary navigation instructions.

Stable idempotency derives from server-stored notification ID/action ID/recipient plus a persisted random invocation ID; resuming a failed attempt reuses that invocation. Editing fields creates a new digest and requires a new app authorization/approval. If an app uses a separate action token, its validation must enforce token-to-client/recipient/URL/method/fields/nonce/expiry binding; an opaque token can refer to app-side state. The provider can bound size/lifetime but cannot validate an opaque app secret. The app is authoritative for one-use replay control, with atomic deduplication/result storage retained through the applicable proof/token retry window and any longer business-idempotency requirement. Tokens are secrets: redact logs, never put in URLs, search indexes, push payloads or analytics.

## Exact-action user verification

Owner-selected interoperability requirement (2026-11-03): apps use one provider-neutral approval verifier with automatic capability/signing-key discovery anchored to the exact issuer and app-specific subject already verified during login. No per-provider app registration, manually configured signing key or provider-specific application branch is required. Never derive trust from an incoming proof’s unverified issuer, embedded key or arbitrary key URL. Discovery uses bounded safe public transport and purpose-separated approval keys, with cache expiry and rotation handling; unsupported providers fail closed for protected actions. The receiving app still supplies the expected user/client/action and enforces current authorization plus atomic replay protection. The generic verifier and discovery extension are requirements, not implemented capabilities.

Owner-selected architecture (2026-11-03): use app-verifiable action approval proofs. The receiving app server must require and validate the proof for protected actions; hiding a button or trusting a browser assertion is insufficient. Waypo verifies fresh user verification and issues narrowly bound approval, rather than relying on custody of broad app bearer tokens to enforce the prompt. Proof issuance does not itself replace the app’s recipient authorization, current action validity or atomic replay/idempotency checks. Proofs are bearer capabilities for one exact invocation and must not enter URLs, logs or notification previews. The reference implementation supports this profile only when explicitly configured and fully ready; production remains disabled.

`verification:"required"` fails closed without a fresh verified WebAuthn ceremony. A provider policy may require UV even when the app does not. A recent login or a button press is insufficient. Approval issuance binds a random server challenge to a canonical versioned digest of issuer, client, app-specific subject, notification/action IDs, exact canonical URL, method POST, ordered fields, optional app-token digest or explicit absence, action nonce, idempotency key and expiry. Preserve exact strings; publish canonical JSON/UTF-8 digest test vectors before implementation.

Use existing SimpleWebAuthn verification with the correct RP ID/origin, challenge, registered credential and `requireUserVerification:true`, and verify the actual UV flag. Single-use challenge consumption and issuance are atomic. The authenticator signs a challenge and authenticator data; it does not prove the person read or understood the fields. The provider UI must display the fields before requesting the credential.

After verification, issue a short-lived (120 seconds in the reference profile) purpose-specific JWS using `jose`, separate signing keys and key discovery from OIDC tokens. The protected type is `waypo-action-approval+jwt`; issuer is the permanent auth issuer, audience is the exact OAuth client, subject is that client's existing app-specific subject, with an action digest binding nonce/idempotency and the full exact action, `iat`, `exp`, `jti`, verification time and explicit verified UV claim. Do not invent `acr` strength or certify biometrics. The app validates allowed algorithms, exact type/issuer/audience, key purpose, subject, digest, expiry and replay binding. Reject OIDC ID/access tokens as approval proofs even if signed by a familiar issuer. This is a provider-attested action approval, not a portable raw WebAuthn assertion to the app (the app is not the provider RP). Proof expiry before first submission requires a new ceremony; an already committed app idempotency result remains retrievable without repeating the side effect.

## Rich content and privacy

Share the existing `packages/auth/rich-message-policy.mjs` contract: 4096 UTF-8 bytes, 256 nodes, depth 16; semantic headings, paragraphs, lists, emphasis, links, code, tables, blockquotes, definition lists and details/summary. No sender styles/classes/IDs/names, scripts, frames, forms, SVG, widgets or auto-fetching media. Native `setHTML` uses an explicit allowlist; lazy cached same-origin version-pinned DOMPurify fallback must apply equivalent restrictions. Identity/UI owns the renderer and browser parity tests. Server admission needs an installed, reviewed structural HTML parser and shared traversal rules; browser-derived plain text is advisory until recomputed server-side.

Extract two distinct normalized strings on ingestion: full searchable text (including closed details content), and disclosure-safe preview (exclude closed details body and all forbidden/hidden/script/style content). Do not search raw markup. Auto preview uses supplied title or first meaningful heading plus a truncated meaningful text preview. Empty or unsupported preview falls back to generic. Push modes are generic default, explicit opt-in auto, or custom explicit bounded title/body. A user/device can only reduce detail; app custom content never overrides a generic device preference. Generic payload includes opaque message reference and provider-owned sender label, no message fields, action tokens or URL query secrets. Sender cannot decide that sensitive text should appear on the lock screen without user permission. Browser/SW receive normalized plain preview, never parse HTML with regex.

## Optional app deadlines

`deadlineAt` is an optional absolute UTC epoch-millisecond timestamp for an arbitrary app-defined due date. `deadlineWarningMs` is an optional bounded suggestion (proposed zero through 30 days), not authority to notify. Display in the user’s timezone with explicit local date/time and accessible full timestamp; preserve the instant across timezone/DST changes. Show app-supplied due-soon/overdue states under sender identity, never as a provider account-deletion notice. Support upcoming, approaching, past and no-deadline filters plus stable earliest-deadline ordering `(deadlineAt,id)` with nulls last. Status derives from the query clock and warning preference; no continuous scheduler wakeups are needed for passive status. A deadline does not delete content, extend retention, expire an action credential, bypass mute or increase push detail. User controls prominence and any reminders. Future scheduled reminders require separate opt-in, bounded jobs/deduplication and privacy/routing checks; they are not implicit in adding a deadline.

## Retention, indexed search and resources

Separate firstSeenAt (immutable earliest meaningful view), read/unread state (reversible), pinnedAt, createdAt and expiresAt. Marking unread does not reset the retention clock. User manual delete removes content, search/index rows and pending delivery/action secrets transactionally, leaving only bounded non-content idempotency tombstones through retry expiry. Pin exempts routine expiry, not account terminal deletion. No silent pin eviction; at pin capacity return a visible capacity error. Show a brief expiring indicator within a configurable short window (proposed 48 hours).

Proposed reference defaults: delete unpinned messages 30 days after first seen; unread backstop 180 days after creation; user may shorten/lengthen within deployment caps or disable seen-relative deletion if capacity permits. App hints may suggest shorter retention but cannot override pin or user policy; expose an earlier hard app expiry as such. Exhaustion rejects new enqueue rather than silently removing unread or pinned messages. Existing account terminal deletion policy still deletes the entire account, including pins. Provider policy and app action-token expiry are separate from content retention.

Provisional per-account caps: 2000 retained messages, 200 pins, 8 MiB charged retained envelope bytes, 16 MiB normalized/search index allowance, 256 app namespaces, 50 results/page, 128 search characters, eight query terms and no arbitrary FTS operators. Quotas also cover enqueue rate, action proof issuance, delegation fetches, push attempts and tombstones. These are engineering starting points requiring measurement, not commercial prices. 2000 × 4096 body bytes alone is about 7.8 MiB; normalized full/plain/preview fields, action/target URLs, tags and bounded verified authority source are additionally charged, so envelope capacity can be reached sooner. Physical SQL/index/WAL overhead is separate; index growth and SQLite write costs must be measured on Node and DO SQLite. Current 32-message cap remains effective until an indexed implementation replaces it.

Introduce a portable transactional notification repository port rather than leaking SQL into the ngin engine. Rows carry owner/client/message keys and indexed app label/title/full text plus state/date/action-status metadata. SQL implementations use owner-isolated FTS5 (availability gated on both runtimes) with transactional insert/update/delete index maintenance; owner-scoped FTS shards or mandatory owner-constrained candidate selection prevents cross-account search interference. Raw FTS query language is escaped/compiled from a small literal-term grammar. If either runtime lacks a safe bounded FTS plan, ship indexed normalized token postings with explicit posting limits; do not fall back to blob scans.

B-tree indexes cover `(owner,createdAt,id)`, `(owner,client,createdAt,id)`, unread/seen/pinned/expiry, deadline and action state. Query planning needs selectivity/cost tests: a LIMIT alone does not bound FTS work. Cap examined candidates (proposed 500), return a continuation/incomplete indicator, and use a transaction/query budget. Stable keyset cursors bind owner, filter/query hash, snapshot upper timestamp/ID and last `(createdAt,id)` under authenticated MAC; sort by newest time/ID rather than unstable rank. Updates/deletions can remove rows between pages but never expose another owner's row. Avoid OFFSET. Search never returns action secrets or raw HTML by default.

Expiration work runs in bounded batches (proposed 50), deletes content/index/actions/delivery jobs atomically, and reschedules the next indexed expiry. Backfill migration is resumable with a version marker and owner partition; no half-indexed rows appear as searchable. Account cleanup includes repository rows, FTS postings, pins, receipts and job references. SQLite deletion is logical deletion; backups/WAL/provider retention remain governed separately and must not be described as immediate forensic erasure.

## Primary references

[WHATWG Fetch](https://fetch.spec.whatwg.org/) defines credential omission, CORS and redirect handling; the selected direct POST profile combines these controls but adds application authorization. [WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/) defines challenge/origin/RP verification and signed user-verification flags; these do not attest informed transaction consent. [SQLite FTS5](https://www.sqlite.org/fts5.html) documents full-text indexing and external-content consistency/deletion duties. These standards support the underlying mechanisms; delegation documents, action envelopes and purpose-specific approval claims above are proposed Waypo extensions.

## Phase 1 implementation increment (2026-11-03)

Implemented locally, with production still disabled: v2 HTML/text admission using maintained `parse5@8.1.0`, shared rich limits, structural safe preview, validated link/target authority, literal-token search, durable summary/full storage separation, first-seen/unread/pin/delete, deadline state/filter/ordering, bounded expiry jobs and terminal SQL/index GC. Protected POST descriptor admission and fresh approval are separately gated behind the complete configured reference composition; disabled providers reject them. The provider-side execute endpoint remains unavailable. Additional-origin validation is implemented only behind an injected safe-public delegation transport; the default composition permits actual HTTPS client-hosting origin and denies foreign origins. Opaque client IDs can receive link-free messages but have no implicit verified web origin.

The shared transactional `tx.notifications` repository runs on actual Node SQLite and SQLite-backed Durable Objects. Non-SQL stores retain the old v1 API but v2 fails explicitly with `notification_index_unavailable`; there is no array-scan search fallback. SQL keeps full HTML/plain text/source in a separate payload column, while bounded candidate queries load only summary/token metadata. A monotonic SQL sequence freezes the cursor snapshot. Owner-bound, filter-bound opaque random cursors persist for 15 minutes, at most 16 per account; this replaces the earlier proposed cursor MAC while retaining server-side binding. Literal normalized Unicode token AND search is the initial contract, not arbitrary substring/FTS operators. The engine examines at most 500 candidate summaries per page; SQLite work can additionally traverse at most the account cap of 2000 message/posting matches for snapshot/keyset predicates, so 500 is not claimed as a raw database rows-read ceiling. Term queries force the corresponding owner/term/order index and posting deletion has an owner/message index. A sparse page can return zero matches with an explicit continuation/incomplete flag. Deadline order places missing deadlines last and uses an expression index.

Initial implementation limits additionally include 512 unique tokens/message, 32768 postings/account and a 16 MiB conservative estimated postings budget. These are admission limits, not claims that SQLite files cannot exceed 16 MiB. Term/index amplification can exhaust capacity before 2000 messages. Node/DO share the same SQL repository and transactional GC. Pin/seen updates change metadata without rebuilding token postings. Existing v1 namespaces migrate lazily, at most eight namespaces per inbox request, each bounded by the historical 32-message cap; `migrationPending` signals incomplete backfill. A per-owner completion manifest prevents reading completed legacy app blobs on every search; a later v1 enqueue reopens only that namespace's migration marker. V1 dismiss removes migrated content/index rows too.

V2 messages use the existing 32-item array only as a pending device-delivery outbox; completed v2 sends leave retained SQL history intact. Inbox-only v2 messages need no delivery-array entry. Existing route/rule/digest authority remains in the ngin engine. Push detail requires explicit app auto/custom selection plus account and route/device opt-in; the default, including legacy app messages, is generic. Delivery does not acknowledge seen. Delayed digest rows remain unpublished until the due job rechecks accepted grant authority; revocation removes their pending content/index rows. Push transport adds an exact opaque `messageId` for a single message and a verified-client-derived HTTPS `senderOrigin`; digest groups use null messageId and open the inbox. Provider notices remain a distinct payload path.

Owner-authenticated same-origin POST APIs under `/api/waypo/notifications/`:

- `inbox`: optional `search`, `clientId`, `unread`, `seen`, `pinned`, `from`, `to`, `expiring`, `deadline` (`none|past|upcoming|approaching`), `sort` (`newest|deadline`), `actionState`, `limit` up to 50 and opaque `cursor`.
- `message`: `notificationId`; returns a full sanitized message without marking it seen.
- `mutate`: `clientId`, `notificationId`, `operation` (`seen|unread|pin|delete`); seen requires `view:foreground-message|explicit-mark`, pin requires boolean `pinned`.
- `navigate`: `notificationId` and optional `actionId` or exact stored `bodyLink` href (mutually exclusive selectors); revalidates current destination authority outside the storage transaction and returns an allowed URL. Initial GET destination ownership is enforced; a subsequently opened app-owned page can navigate its own tab and the provider cannot constrain that later app behavior.

## Configured protected-action profile

`packages/action-approval/` now implements a provider-neutral approval core, separate from notification execution. Its [interface and security contract](../implementation/action-approval-core.md) defines canonical binding/digest vectors, separate provider/app-server entries, purpose-specific ES256 JWTs, expected authenticated issuer/sub/client anchoring, injected bounded discovery, trusted internal ceremony receipt consumption and a separate optional invocation ledger. The proof binds notification ID, action ID/version, exact URL/method/ordered fields, action nonce/expiry, recipient identity and stable idempotency key. App-issued authorization-token digest is optional with explicitly bound absence, rather than a mandatory extra gateway token.

The configured reference composition now admits protected POST descriptors, captures the recipient subject through official authenticated UserInfo, verifies fresh action-bound passkeys, and exposes a dedicated owner-bound confirmation page. Optional discovery advertises `notifications.protected_post` only when the complete composition is ready. Omitted/disabled configuration does not advertise it. The legacy provider executor still rejects POST: submission is foreground browser-to-app. Pure-core tests use real JOSE cryptography with synthetic ceremony DI; separate real Node/Worker browser gates cover signed assertions and app verification. Receipt-port registration prevents JSON substitution; it does not prove a provider actually performed WebAuthn. The selected issuer attests the action/UV, and a malicious/compromised provider can mint that attestation as it can mint logins. Generic discovery removes manual provider configuration, not inherent issuer trust or the need for stronger app assurance policy when required. No `acr` or certified global assurance is invented.

Verification is pure; invocation claim, pending lease, terminal result and reconciliation are separate. The app must commit its effect/result atomically or use an independently idempotent executor. Expired pending leases are indeterminate and never automatically taken over. An authenticated app result route may expose an existing committed outcome after proof expiry, but expired JWT verification still fails. The configured reference client submits directly with credentials omitted, redirects rejected and no automatic retries. An ambiguous outcome requires checking the app before retrying. This does not solve every browser-private-address boundary or enable a provider-side executor.
