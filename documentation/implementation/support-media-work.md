# Support media work admission

> Source-development reference: open-source combined candidate `c8698ac`, selected by this isolated hosted source pin. Production/public operation remains disabled; paired engine and authenticated UI/hosted qualification remain separate gates.

Support media is optional provider implementation functionality. It is independent of the public app storage allowance and is unavailable without a configured media validator. Worker composition currently supplies no validator; enabling a configuration flag does not establish a safe Worker decoder. Self-hosted support remains disableable.

When installation period budgeting and support media are enabled, configure explicit `support.mediaWork` with exactly `revision`, `uploadBaseUnits`, `uploadPerMiBUnits` and `readPerMiBUnits`. The revision is a nonempty string up to128 characters; each cost is a positive safe integer no greater than1,000,000. Values are copied/frozen. There is no runtime default and no monetary guarantee. An illustrative engineering profile could charge upload10,000 plus1,000 per started MiB and reads1 per started MiB. These examples are not approved launch values or equivalent to notification CPU cost. Changing weights never resets the anchored period wallet. Application composition mounts a trusted optional reservation callback whenever a period budget exists. Active/wind-down media:true requires valid weights at startup. Text-only and disabled support remain configurable without them; retained media access without weights fails closed before object/decoder work, so disabling upload UI never creates an unmetered download path. Missing-policy HTTP503 carries a finite five-minute recheck hint without exposing configuration internals.

The trusted engine constructor receives `reserveWorkInTransaction(tx,{kind,bytes})`. Operation kind and byte count come from server-selected upload bytes or authorized stored metadata, never a public essential/exemption field. Admission happens after live ticket/user/staff authority and quota checks, before object writes, validation or object reads. The reservation shares the existing metadata transaction with stage creation/auditing; failed commit rolls back both and performs no external work. Later validation failure, lost response or abandoned stage never refunds work. A bounded already admitted object/decoder pipeline can finish across a period boundary; it remains charged to its admission period.

Only media uploads/downloads use this optional pool. Text appeals, ticket access and replies, account check-in/export, and support garbage collection retain their existing authority and availability. Disabled support does not allocate new support state. Full finite daily/monthly Retry-After guidance passes through support HTTP; generic clients must not automatically retry an unsafe upload create merely because a503 is retryable.

The standalone HTTP shell bounds JSON bodies to16KiB and media bodies to5MiB while reading, with a ten-second deadline. It rejects oversized input before concatenating or invoking storage/decoder work. The shipped Node validator has a process-wide maximum of two active validation pipelines, no waiting queue, and a503/one-second hint when busy. A permit covers sequential ffprobe and ffmpeg execution, including actual child settlement after SIGKILL on their five/ten-second deadlines. The one-or-two-pipeline limit is a shipped internal process resource guard, independent of storage quota; it is not a promise that larger Node deployments cannot support a separately validated resource profile. This guard is not a decoder sandbox or a claim that arbitrary operator binaries cannot spawn descendants.

The prior global64-ticket and128-audit hard stops are replaced by the bounded paged repository described in [support storage and migration](support-paged-repository.md). Its finite engineering counts and logical byte budgets do not establish financial safety. Repeated staff/control-plane work, decoder sandboxing, raw incoming Worker costs and other economic paths remain separate work.
