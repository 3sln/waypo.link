# Hosted email admission proposal

Design and release-gate audit, 2026-11-03. The isolated portable budget engine and thin hosted constructor now exist under packages/policies/email-budget.mjs and hosted/waypo/email-budget.mjs; the native hosted composition now requires the shared DO admission path described below. Configured core public email human admission is now wired, and native hosted composition requires production-mode email-purpose verifier configuration. See the portable implementation contract for its exact bounded current semantics. The earlier proposal below records rationale; current core HTTP and hosted shared-DO integration contracts govern implemented behavior, and production sending is not enabled. Native email transport readiness does not establish economic readiness.

## Current evidence and launch gap

Portable `BeginEmailAction` admits at most 64 live flows per identity store and three per normalized recipient, each lasting ten minutes. Flow credential verification has five attempts. These constrain outstanding identity state, not fleet sending over a day/month. They do not cap all lifecycle sends, cross-installation activity or the provider bill. Native magic-link request/verification HTTP routes are blocked; the maintained initiation path calls the native API with internal flow context, and its send callback rejects absent context. Preserve these bypass fences.

Public request admission already offers bounded durable category/peer reservations and service work credits demonstrate prepaid durable reservations surviving cache/process loss. Neither currently debits a unified email budget. Existing public admission hashes short-lived peer identifiers; the proposed mail budget does not collect IP or location and should not add either. The configured email-initiation path now uses a separate strict Turnstile purpose, in addition to passkey enrollment and retention check-in. The installed Better Auth magic-link plugin declares five requests per 60 seconds for /sign-in/magic-link and /magic-link/verify; these HTTP paths are blocked by our wrapper, while maintained email/start invokes auth.api.signInMagicLink internally. That plugin rule is not a demonstrated limit on the maintained outer initiation route and must not be counted as fleet protection. Provider sessions explicitly discard stored IP addresses; its native limiter uses a trusted transient-peer header, which must not become persisted mail-budget metadata.

Cloudflare's [current pricing](https://developers.cloudflare.com/email-service/platform/pricing/) requires Workers Paid for arbitrary recipients, includes 3,000 messages per account/subscription billing month and charges $0.35 per additional 1,000. Accepted messages, including hard bounces, count; API-boundary rejection does not. Verified account destination sends are free. These are vendor facts, not approved Waypo prices or configured budgets. The [limits page](https://developers.cloudflare.com/email-service/platform/limits/) describes dynamic per-account daily limits based on sending history, without a fixed public daily number; it currently allows 50 combined recipients and 25MiB per message. Our stricter one-recipient/plaintext profile remains unchanged. Workers/storage/verification costs are additional and require their own work budgets.

## Proposed smallest trusted port

A private `createEmailBudget({store,clock,recipientKey,policy})` exposes `chargeAttempt({attemptId,purpose,recipient})` and bounded `collect({limit})`. No send/fetch port or public route. Trusted orchestration validates/templates first, then charges immediately before each actual native send. Recipient and purpose derive from trusted delivery data; app callers cannot select a priority pool. The durable store must be fleet-wide for the actual Cloudflare billing account, not one DO per user/installation; one serialized SQLite/DO transaction checks and debits all applicable counters. Failure/unavailability rejects before sending. No network awaits in that transaction.

Success returns an opaque immutable admission record for one immediate in-process dispatch, not a reusable client capability. A repeated attemptId returns already-charged without permission to dispatch again. Every real retry needs a new attemptId and new charge. Crash after charge/before send conservatively loses the slot. Crash/timeout/API failure after dispatch never refunds: unknown outcomes may have been billed. Accepted/rejected status can be counted separately for diagnostics but cannot restore spend/message capacity. Store deletion, migration or policy revision must not reset active period totals. A signing secret/config revision is not a quota namespace.

Required explicit policy fields: stable billing-account namespace; revision; currency; integer conservative maximum cost per attempt in configured currency microunits; total daily/monthly attempt and cost ceilings; short-window fleet and recipient capacities/refill/window; separate private-provider-notice, public-login and app pools; reserved notice allocation; max active recipient buckets and attempt entries plus explicit attempt/recipient/owner state reservations for private notices; attempt TTL, recipient window TTL and bounded GC batch. All positive bounded engineering limits are validated. No commercial values or defaults are proposed. Calendar UTC days/months are acceptable explicit application budget periods; they are not claimed to equal Cloudflare's subscription cycle. Configure ceilings conservatively, or explicitly supply validated subscription-cycle boundaries. Budget every attempted arbitrary-recipient send at the conservative paid rate without assuming free allowance; cost is an admission estimate, not an invoice guarantee. Configuration must be updated before a vendor price increase; stale/unknown price revision fails closed for production.

The absolute fleet ceiling includes reserved notices. Ordinary pools cannot consume the reserved portion; private provider lifecycle/security notices use only server-generated purpose, their own finite rate/cost limits and the same absolute ceiling. Account notices can be delayed under exhausted capacity; mandatory account deletion/retention does not wait forever for mail acceptance. There is no unlimited emergency bypass. Apps/digests remain disabled until tenant/app quotas and their explicit funding/work policy are implemented.

Public login uses one uniform pool for both known and unknown addresses, with equivalent public responses and admission ordering. Never select a public success versus 429 based on known-account status or expose reserved-pool availability through the initiation response. Current terminal-account nonissuance remains generic. Internal delivery status and suppression diagnostics do not become an account lookup API.

## Human admission before public email

Reuse the isolated challenge origin, extending the purpose allowlist deliberately with `email-initiation`; do not relabel a passkey-enrollment proof. A server-issued short-lived ticket binds exact issuer, purpose/action, random nonce/operationId, browser-secret hash and normalized recipient keyed digest. No raw email in the third-party challenge payload. Siteverify must validate exact configured challenge hostname and action, and bind returned cdata to the server ticket/nonce using existing safe opaque format. Consume one-shot ticket atomically with local initiation admission before any dispatch; require current browser binding and reject changed address, replay or expired proof. Human verification proves neither mailbox ownership nor account existence and does not replace the fleet budget. Do not send `remoteip` or retain raw IP/location. Apply bounded cheap ingress admission before allocating challenge state or calling Siteverify, then durable recipient/fleet/spend admission before sending. Malformed and denied requests must not cause native sends.

Route tests must exercise direct native magic-link endpoints, auth API invocation without internal flow, alternate admin origins, payload email changes and replay. Only trusted internal composition may invoke the native API after completed admission; an HTTP boolean or body-carried reusable admission token is insufficient. Existing host/origin/CSRF validation remains necessary. Decide the public generic response policy explicitly so delivery outages and account status do not create enumeration differences.

## Storage, privacy and tests before wiring

Recipient buckets use keyed HMAC of the same normalization as identity, domain-separated by mail budget and bounded rate window; no unkeyed enumerable email hashes. A short overlapping window implementation must prevent boundary rotation bypass. Retain current/previous relevant buckets only until their rate period ends plus bounded retry margin. A dedicated bounded expiry index allows incremental physical deletion; no every-request global scan. Capacity exhaustion fails closed instead of evicting an active recipient bucket and granting fresh quota. Counters contain no message, login code/link, recipient plaintext, provider errors or raw IP. AttemptId must be random server-generated and uncorrelated with recipient. Aggregate spend/day/month history has explicit short retention; attempts expire only after their no-resend contract, while period totals survive until period expiry. No automatic refund or reset on collection.

Required tests: concurrent final slot across installations; all purposes share absolute ceiling; public login cannot drain notice reserve; unknown/known recipients expose equal admission behavior; daily/monthly boundary and clock rollback; price/policy revision without counter reset; repeated attempt and ambiguous delivery not refunded; crash after debit; bounded recipient flood; HMAC rotation/window overlap; bounded GC removes only expired state; SQLite rollback/restart/isolation. Integration tests must prove the actual delivery closure cannot bypass charge, human proof precedes public email sends, and disabled/no-policy configuration performs no native send. This proposal needs interface approval before an isolated leaf is implemented; core application/composition are currently owned by the identity coordinator.

## Private shared Durable Object integration

Native EMAIL composition now requires an actual private EMAIL_BUDGET namespace, HOSTED_EMAIL_BUDGET_CONFIG JSON `{billingScope,policy,gcIntervalMs}` and canonical base64url HOSTED_EMAIL_BUDGET_KEY containing32–64 random bytes. Missing infrastructure fails closed before constructing native delivery. There are no commercial policy defaults. The private bridge always injects the required beforeEmailAttempt hook. Legacy/no-native binding startup remains unchanged. Native composition also requires emailHuman.required:true and constructs the maintained production email-purpose verifier; this is configured protection, not externally verified vendor/domain readiness or complete production readiness.

The only object name is waypo-email-fleet-v1, independent of installation, policy revision and billingScope. The actor checks its actual ctx.id against that fixed namespace name. A permanent SQL identity row pins billingScope and key fingerprint; changing either rejects rather than creating empty counters under another key. Per-request configuration fingerprint deterministically covers the complete canonical policy, interval, scope and key fingerprint. It detects inconsistent sender/ledger configuration; it is not public-caller authentication. No raw key, recipient or code occurs in that header. Namespace binding possession is the private authority boundary; every authorized caller must still derive purpose from trusted provider state. The leaf does not independently certify that callers may choose private notice purposes.

All installations sharing the provider bill must bind the SAME ACTUAL namespace, not merely use the same binding name/class or copy a billingScope. A different namespace is a different database; local code cannot cryptographically detect an operator replacing it with a new empty one. Deployment inventory/change control and independent integration evidence are required. The dedicated email-budget-worker.mjs has a404-only public fetch; only its private DO binding supports exact POST https://email-budget.invalid/attempt with bounded2KiB `{attemptId,purpose,to}` and bounded256-byte admission results. It mounts no public budget/mail delegation. The sender's leaf deadline also bounds private admission; late/unknown charges never resume a send or refund.

The actor runs the portable engine using materialized SQL reads/writes inside actual ctx.storage.transaction(async ...), including alarm scheduling, without network work in the transaction. This follows the [current official SQLite storage transaction contract](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transaction), which includes top-level storage SQL operations in an async storage transaction. It does not assume the128KiB key-value value limit accommodates the full bounded state row. The configured SQLite-backed class is required.

The actor owns alarms independently of provider API/preview/EMAIL enablement. Each successful admission schedules finite GC at configured gcIntervalMs, no greater than attempt TTL/recipient window. Each alarm runs at most five256-entry collection passes; when all recipient/attempt/owner rows are gone it deletes its alarm, retaining the fixed pin and aggregate counters rather than endlessly waking an inactive ledger. Alarm errors preserve state and schedule persisted exponential backoff starting at least60seconds, capped at one hour; restart/new admissions do not erase that backoff. After a successful explicit failure reschedule, the handler returns normally with a fixed safe diagnostic, so it does not also request automatic exception retries. If persisting the retry itself fails, the exception may invoke Cloudflare’s bounded native retry mechanism (currently exponential delay starting at two seconds, up to six retries; see [official alarm contract](https://developers.cloudflare.com/durable-objects/api/alarms/)). There is no minimum-frequency claim during that storage-failure case. A successful maintenance pass clears failure metadata and restores normal configured cadence. Persistent errors delay physical collection and require operator repair; they never reset quota or permit sends. Retained config/key must remain available to the dedicated ledger after disabling native EMAIL in sender Workers.

`wrangler.email-budget.example.jsonc` describes the separate private shared namespace; wrangler.email.example.jsonc binds it externally. Both keep routes empty and previews/workers_dev disabled. Budget config values are deliberately invalid operator placeholders and secrets are omitted; no deploy/send is authorized by these examples. Actual workerd tests use two sender Worker instances sharing one actual ledger namespace, a fake native send capability and explicitly synthetic pricing/caps. They exercise global races, unknown send charging, duplicate refusal, private reserve, SQL rollback, restart, configuration/key pin failure, bounded physical GC with EMAIL absent, alarm failure rescheduling and no public delegation. These are local runtime proofs, not a real Cloudflare send or deployment.

Waypo.link production currently rejects explicit legacy EMAIL_TRANSPORT bindings, even when human admission is configured, because an unreviewed legacy sender could bypass the shared economic guard. The chosen production path is native Cloudflare EMAIL with mandatory human admission and the actual shared budget DO; no-email production is allowed. Sandbox legacy tests and portable OSS custom transports remain supported. This is a hosted implementation restriction, not a protocol requirement; future legacy budget adapters require separate review.
